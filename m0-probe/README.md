## 怎么跑

```bash
cd m0-probe
npm install          # 首次
npm start            # 交互模式：打开卡片 + 控制台，逐条测
npm run selftest     # 自检模式：自动跑完能自动的，导出报告后退出
npm run calibrate    # 考裁判：故意把代码改错，看测试敢不敢报警（跑完自动还原）
npm test             # 离线考裁判：不需要 Electron，纯 Node 跑四组测试
npm run test:names   # 只跑产物命名契约的考裁判（15 条恶意后缀 + 3 个变异体）
npm run test:verdict # 只跑焦点判定的考裁判（9 条用例 + 3 个变异体）
npm run test:crash   # 只跑失败语义的考裁判（5 关，含子进程角色扮演）
npm run test:flags   # 只跑诊断开关解析的考裁判（24 条用例 + 3 个变异体 + 源码接线检查）
```

> **`npm test` 是什么？为什么它不需要 Electron？**
>
> 它是**把"判定逻辑"和"采集逻辑"切开之后的产物**。凡是不需要 Electron 的逻辑，
> 一律拆成**零依赖模块**，这样它就能在 CI / 沙箱 / 无头环境里被验证 —— 不需要启动 GUI。
>
> | 模块 | 职责 | 谁测它 |
> |---|---|---|
> | `src/main/focus-verdict.js` | 焦点测试的**判定**（三态） | `tools/test-focus-verdict.mjs` |
> | `src/main/crashlog.js` | 失败语义：落盘 + 退出策略 | `tools/test-crash-policy.mjs` |
> | `src/main/artifact-names.js` | 自检产物的**命名契约**（隔离后缀） | `tools/test-artifact-names.mjs` |
> | `src/main/diag-flags.js` | 诊断开关的**解析口径**（`M0_DIAG_RESIZABLE`） | `tools/test-diag-flags.mjs` |
> | `src/main/window.js` | **采集**（真实 focus 事件） | 只能真跑 → `npm run calibrate` |
> | `src/main/blurmeasure.js` | 模糊测量 + 内建校准 | ⚠️ **仍绑在 Electron 上**，见 TD-06 |
>
> **四组测试都用变异测试（mutation testing）**：除了断言"好实现要通过"，
> 还要求"**已知坏掉的实现必须被抓**"。只要有变异体存活，就判 FAIL ——
> 因为那证明**这份证明本身是无效的**，不是证明对象没问题。
>
> 这条规则已升格为 `项目规则.md` **R-B11**（不需要 Electron 的逻辑，不许被 `electron` 的 import 绑架）。

> **`npm run calibrate` 是什么？** 一个**检查"检查本身"是否有效**的工具。
> 它会临时把 `window.js` 里的 `showInactive()` 换成 `show()`（这必然让卡片抢焦点），
> 跑一次自检，确认验收 3 **报 `fail`**，然后**逐字节还原**。
> 退出码：`0` = 裁判有效 / `1` = **裁判是假的**（植入错误后仍报 pass）/ `2` = 没测到（不许冒充前两者）。
> 详见 `docs/05-M0验收记录.md` §6.4 第 4 条。**2026-09-19 实测结论：`CALIBRATED · 裁判有效`。**
>
> ⚠️ **`0` 是绿、`1` 是红、`2` 是灰 —— 灰不等于绿。** 三态不许合并（`docs/05` §6.4 第 4 条）。
>
> ⚠️ **它会真的启动主进程，因此带一个"污染留痕"的坑（已修）**：主进程照常把报告写到
> `report/_selftest-report.md` —— 也就是**验收记录的证据本体**。所以那次"故意改坏"的运行会**覆盖它**。
> 2026-09-19 实际发生过一次（留下一份写着「M0 未通过」的假记录，还差点误导人去走降级预案）。
> 现在有两层保护：**① 隔离** —— 校准器传 `M0_SELFTEST_TAG=.calib`，那次自检的产物另存 `*.calib.*`；
> **② 守卫** —— 跑前快照、跑后**逐字节比对**正式留痕，被改动就**立刻还原并告警**（不依赖"环境变量一定传到了"这个假设）。

> ### ⚠️ 不要直接跑 `electron .`
>
> **所有启动都必须走 `npm start` / `npm run selftest`**，它们内部调 `tools/launch-electron.mjs`。
>
> **原因**：本机环境预设了 `ELECTRON_RUN_AS_NODE=1`（不少 Electron 宿主应用会把它泄漏给子进程）。
> 只要它存在，`electron.exe` 会**静默退化成「普通 Node」**：不开窗口、不注入 Electron API，
> 然后抛出一句完全误导的错误 `does not provide an export named 'BrowserWindow'`。
> **这个变量在进程启动时被读取，进程内无法自救** —— 只能在启动器里于 `spawn` 之前删掉。
>
> 裸跑只保留给对照排查：`npm run probe:raw`。
>
> **为什么严重**：你会以为自己在测 Electron，其实什么都没测，还可能拿到一份"看起来跑通了"的假数据。

> **装不上 Electron 二进制时**（国内网络常见）：
> ```powershell
> $env:ELECTRON_MIRROR="https://npmmirror.com/mirrors/electron/"
> node node_modules/electron/install.js
> ```

## 拖动把手：怎么用，以及它为什么拖不动（2026-09-20 第二次修订）

> ⚠️ **本节的结论与上一版相反。** 上一版写"已补上拖动把手"，实际结果是**实测拖不动**。
> 按本项目规矩，**留痕与事实不符必须改** —— 所以本节重写为一次**诊断**，而不是一份说明书。

**收起态**：把手在卡片最左端（点阵 ⠿）。**展开态**：把手在标题行最左端。

### 为什么是"显式把手"，而不是"整张卡片都能拖"

因为 `-webkit-app-region: drag` 有个**必须知道的副作用**：

> **设了 drag 的区域会吞掉该区域内所有鼠标事件 —— 包括 `click`。**

而 `card.js` 里 `#bar` 的 `click` 正是**"展开卡片"**。所以：

- ❌ 把整条 `.bar` 设成 drag → **展开功能直接消失**（点了没反应，且**不报任何错**，属静默失败）
- ✅ 只在把手这一小块开 drag → 拖动与点击各得其所

**这条对 M1 同样成立**：任何时候想给卡片加"整块可拖"，都得先确认那块上有没有点击交互。

### 现状：把手存在，但拖不动（根因已定位到高置信、本机尚未复现）

| 层次 | 内容 |
|---|---|
| **本机已验证** | ① 卡片窗口 `resizable: false`（`src/main/window.js`）；② `card.js` 里**没有任何 JS 拖动代码** —— 拖动**唯一**依赖 `card.css` 的 `.grip { -webkit-app-region: drag }` |
| **外部证据支持的高置信推论** | 同一无边框窗口配置下，把 `resizable` 改回 `true`，拖动**立刻恢复** → 推论：**`resizable: false` 使拖动区域失效** |
| **仍未验证** | 透明窗口的 hit-test、`showInactive` 下"第一击只用于激活窗口"这类机制是否也有份 |

**两条必须知道的边界**：

1. **`-webkit-app-region: drag` 在 DevTools 打开时会失灵**（Electron 官方文档载明）——
   诊断时**别把 DevTools 常开**，否则会拿到假结论；
2. **drag 区吞掉鼠标事件是 OS 限制、无法绕过**（`electron#29891`，官方回复定性）——
   这反过来证明"用独立把手、不整条 bar 设 drag"的设计是对的。

### ⭐ 拖动把手的诊断（本轮主要动作，要跑两次）

**为什么需要诊断**：上面那条根因目前是**推论**，不是**已验证**。本项目对这两者的区别很敏感
（`R-A04`：不确定就说不确定）—— 写进留痕的推论必须标明它是推论。

**准备**：新增了**零依赖**模块 `src/main/diag-flags.js`，由一个临时环境变量控制开关；
默认**关闭**（`resizable: true` 有真实代价：用户可以拖窗口边缘改尺寸，而验收 6 要的是精确的固定尺寸）。

```powershell
cd m0-probe
npm start                                 # 第 1 次：默认态（开关关）
```

```powershell
cd m0-probe
$env:M0_DIAG_RESIZABLE="1"; npm start      # 第 2 次：诊断态（开关开）
```

**每次都记四件事**：

| # | 看什么 | 怎么看 |
|---|---|---|
| 1 | **把手能不能拖** | 按住卡片最左端的点阵手柄（⠿），拖一段再松手 |
| 2 | **终端有没有 `[diag] 卡片窗口 resizable=… movable=…`** | 主进程终端输出。**这一行是无条件打的**，专门用来确认"开关到底生效没有" |
| 3 | **终端有没有 `[M0] grip mousedown 到达了渲染层`** | 本轮加的**判别探针**，判据见下表 |
| 4 | **拖动时卡片有没有抢焦点** | 若会抢，就与验收 3「不抢焦点」产生张力（"用户主动拖"算不算抢，是个要记下来的口径问题） |

**判据表（第 3 件事为什么有判别力）**：

| 现象 | 含义 |
|---|---|
| 日志**打出来**了 | `.grip` 是个**普通元素**，`-webkit-app-region: drag` **没有**被注册 → 与「`resizable: false` 让 drag 失效」这一推论**一致** |
| 日志**没打出来** | drag 区**已经注册**并生效，它按 Windows 的既定行为吞掉了鼠标事件，但 OS 层级的拖动没发生 → 问题**不在"区域没注册"**，得往别处查 |

两种结果指向两个不同的原因 —— 这才叫"有判别力的探针"，而不是"跑一次看看"。

两次跑完，**无论结果如何都要回写 `docs/05-M0验收记录.md` §1 验收 8**：诊断结论 + 你看到的四件事。
**"没跑成"也是一种结果，必须写。**

### 修法方向（已定，待诊断结论后实施）

**整体替换为 JS 手动拖动**：`mousedown` → IPC → `setBounds`。

为什么不修 CSS 那一行、而要换掉：**要换的是实现方式，不是参数。** 把 `resizable` 改成 `true` 只是**诊断手段** ——
长期打开会让人拖窗口边缘改尺寸，而**验收 6 要的恰恰是精确的固定尺寸**（360×44 / 360×520）。

### 顺带修掉的死键（2026-09-20，用户反馈「存在大量无行为（无动作/无进展）的按键」）

排查结论：卡片上 6 个可交互元素里**4 个是死的** —— 两个把手 ＋ 底栏两个按钮。

| 元素 | 原来 | 现在 |
|---|---|---|
| `.grip` ×2 | 只有 CSS，拖不动 | 待换成 JS 拖动（本轮加了诊断探针） |
| `#btn-refresh` 刷新 | 只调 `api.log()` → **日志进主进程终端，卡片上零变化** | ✅ **真实行为**：重报渲染事实 ＋ 更新条数标签 ＋ 弹 1.4 秒轻提示 `.toast` |
| `#btn-settings` 设置 | 同上 | ✅ 改为 **`disabled`** ＋ `title="设置面板将在 M1 开放"`（M0 没有设置面板，**禁用比伪装成可用更诚实**） |

**根因链（值得记住）**：`card.js` → `api.log()` → `IPC.LOG` → 主进程 `console.log('[renderer]', …)`。
**日志进的是终端，不是界面。**"发了日志"不等于"有反馈"。

**控制台（`probe.html`）是另一回事**：15 个按钮**全部有真实绑定**，逐条核过 —— **不是重灾区**。

⚠️ **这两类必须分开记**："绑了个只写日志的空壳"是真缺陷，"有行为但看不出来"是反馈强度问题 ——

## A10 桌面层挂载实验（2026-09-22 结案 · 工具与两条教训）

> **背景**：ADR-011 曾把卡片层级定为「桌面层」，并给 M0 追加了验收 **A10** 来证明"挂得进去"。
> **结论：挂不进去** —— 判据①「仍可见」FAIL ⇒ **ADR-012 改用「置底顶层窗口」**，该退路**已实测可行**。
> 正式结论见 `docs/05` §1 · 追加验收 A10 与 §0.3；决策见 `docs/03` ADR-011 / ADR-012。

### 三个工具（都在 `tools/`）

| 工具 | 干什么 |
|---|---|
| `attach-to-desktop-layer.ps1` | **主角**。四模式：`probe`（只看结构、不动手）/ `mount`（自建测试条 → 实验 → 自动还原）/ `attach -Hwnd <句柄>`（挂已有窗口）/ `detach`（还原）。参数：`-ZOrder above\|below`、`-Target progman\|workerw`、**`-Placement wallpaper\|bottom`** |
| `lint-ps1.ps1` | **离线静态检查器（C1–C5）**，专治本工程这类 P/Invoke 脚本的高频坑，能在"跑起来之前"抓结构损坏 |
| `win-display-facts.ps1` | 独立裁判（验收 9 用的那条链路），也用来给挂载实验提供 display 事实 |

```powershell
cd m0-probe
powershell -File tools/attach-to-desktop-layer.ps1 -Mode probe                          # 只探结构，安全
powershell -File tools/attach-to-desktop-layer.ps1 -Mode mount -Placement bottom        # 完整实验，自动还原
powershell -File tools/lint-ps1.ps1                                                     # 离线静态检查
```

> ⚠️ **跑 `mount` 之前先 `Win+D` 露出桌面**，否则会把"挂载成功"误判成"被覆盖"。
>
> ⚠️ **改过 `.ps1` 结构后必跑 `lint-ps1.ps1`** —— 它是唯一能在运行前抓到结构损坏的网
> （已真抓到过一次：插反的注释块把整个 `.ps1` 变成未终止的块注释）。
> 另外：**临时补丁脚本用完要删** —— `.ps1` 缺 BOM 会让 lint 判 FAIL。

### ⭐ 教训一：一个"看起来很漂亮"的假读数

首跑（`report/desktop-attach-mount.rev4-bottom.json`）报：

```
ourIndex = 36   progmanIndex = 422   weAreAboveDesktop = true   → 判据① PASS
```

**看着全对，实际全错。** 症结：**`weAreAboveDesktop` 对"排在最顶"和"排在最底"同样为真** ——
真·置底应让 `ourIndex` 贴着 `progmanIndex`（即 `421 / 422`），而 **`36` 在 421 个顶层窗口里太靠上**。

**根因**：脚本先 `PlaceBottom()`、后 `MoveTo()`，而 `MoveTo()` 传的 `hWndInsertAfter` 是 `NULL`（= **`HWND_TOP`**），
**把刚压到底的窗口重新提回了最顶**。

**修法**：顺序交换为「**先定位、后压底**」，并**新增距离判据**。报告里因此多了两个字段：

```
placeBottomEffective = (progmanTL - ourTL) <= 3
gapToDesktop         = progmanTL - ourTL        → 真·紧贴桌面之上时 = 1
```

> ⭐ **由此立规**：**凡「置底 / 置顶」类实验，一律用距离读数（`gapToDesktop`）验收，不许只看 `weAreAboveDesktop`。**
> 后者对两个极端都返回 `true`，是个**没有分辨力的判据**。

### ⭐ 教训二：正对照 ＋ 自校准分辨力（这次真的救了结论）

脚本从 rev3 起就带**内建正对照**：每次测量都先在**尚未挂载**的同一窗口上采一次。
读数（`report/desktop-attach-mount.rev4b-bottom.json`，`stage=complete`、`errors` 空）：

| 阶段 | nearRatio | 含义 |
|---|---|---|
| 窗口建好后（**正对照**） | **0.953** | 窗口确实画在屏幕上 |
| 挂进桌面层后 | **0.491** | **＝ 壁纸基准**，增量 **0.000** |
| 销毁窗口后 | 0.541 | 回到背景 |

判据用**增量**与**校准出的分辨力**比：`power = 0.462`，增量 `0.459` ≥ 阈值 `0.231` ⇒ **判定有效**。
⇒ 结论**不是"看不出差别"**，而是**"确实没有任何可见变化"**。

同时，退路「置底顶层窗口」的读数是 `ourIndex=419 / progmanIndex=420`（共 421）、`gapToDesktop=1`
⇒ **紧贴桌面之上、排在其它所有窗口之下**，判据① PASS（增量 0.459）。

### ⚠️ 覆盖缺口（别把本结论外推）

- 只在本机 **Win11 25H2 build 26200.9457** 验过；**社区流传的 24H2 配方（`below`+`layered`）在本机同样不成立** ⇒ **不可外推到其它 Windows 版本**。
- 只测了"静止可见"，**没测 Win+D / 独占全屏 / 任务栏自动隐藏** 的交互。
- 挂载实验的验证对象是**系统 `Button`**（自建测试条），**不是真实 Electron 卡片**（`transparent` ＋ `backdrop-filter`）。

## 验收 9 的做法：给 Electron 找一个独立裁判

这是整个 M0 里最需要花心思的一处。

**问题**：验收 9 要判断 `getPrimaryDisplay().scaleFactor` 可不可信。
但如果只用 Electron 自己的 API 去验证 Electron 自己的读数，**等于自己给自己判卷** —— 读数错了也测不出来。

**做法**：绕过 Electron，直接问 Windows。

```
tools/win-display-facts.ps1
  └─ P/Invoke 调 EnumDisplaySettingsW
     └─ 拿到每块显示器的【真实物理分辨率】与【物理坐标】
```

然后交叉校验**两条独立证据链**，任一条对不上就判读数不可信：

| 证据 | 判据 |
|---|---|
| **A · 分辨率一致性** | `display.size(DIP) × display.scaleFactor` 应当等于 Windows 实测的物理分辨率 |
| **B · 缩放比一致性** | `scaleFactor` 应当等于 Windows 的 `logPixels / 96` |

**还有第三路佐证**：渲染进程的 `window.devicePixelRatio`。它和主进程的 `scaleFactor` 是两条不同的代码路径，两者不一致就说明主进程那条有问题。

> **这个"找独立裁判"的做法已经升格为流程约定**：见 `docs/03-工程架构文档.md` §5.7 ——
> 每当要新用一层平台能力，先写独立裁判或对照实验，再写业务代码。

## M0 踩到的六个坑（B8–B13）

> 前五个全部是**静默失败**：不报错、不崩溃，只是结果不对。
> 第六个（B13）不静默，但同样只有真跑一遍才看得见 —— 而且它**推翻了我自己的判断**。
> 完整描述见 `docs/04-项目审查报告.md` §6；这里只写"工程上怎么应对"。

### B8 · `sandbox: true` 与「词汇表唯一」不可兼得

**现象**：`sandbox: true` 下 preload 的 `require` 是受限 polyfill，**不支持 `require` 本地文件**。

| 要求 | 出处 |
|---|---|
| `sandbox: true` | 安全基线（审查报告 B2）—— 本应用要渲染外部不可信内容 |
| 词汇表只能有一个来源 | 架构铁律 D6 |

**处理：不偷偷降级 sandbox，改成「内联 + 自检」。**
preload 内联一份只读通道表 → 通过 `__channels` 暴露 → 主进程启动时逐项比对 → 不一致就报出来。
**自检实测：通过（21 条一致）。"重复"已从隐患变成被机械检查的不变量。**

**产品阶段建议**：引入 esbuild，把 preload 打成自包含 CJS，既保住 `sandbox: true` 又消除重复。

### B9 · `file://` 下 CSP 的 `'self'` 可能匹配不上

**处理**：CSP 显式加 `file:` 方案源。**另注**：`probe.html` 初版用了内联 `style="..."` 被 CSP 拦下 —— **禁止内联样式，全部走 class**。

**产品阶段建议**：改用自定义协议（如 `app://`）提供渲染层资源，这样才有正常源语义。

### B10 · ESM 主进程顶层 `await app.whenReady()` 死锁

**现象**：一个窗口都不出现，进程却不退出，**没有任何报错**。
**原因**：Electron 要等入口模块求值完毕才发 `ready`，而顶层 await 正在等 `ready`。
**处理**：一律写 `app.whenReady().then(...)`。已升格为 `项目规则.md` **R-B07**。
**复测**：`node tools/launch-electron.mjs experiments/diag-tla-deadlock.mjs`

### B11 · `ELECTRON_RUN_AS_NODE=1` 让 Electron 静默退化成 Node

见本文开头那个 ⚠️ 警告框。已升格为 `项目规则.md` **R-B09** + ADR-010。
**复测**：`node tools/launch-electron.mjs experiments/diag-electron-api.mjs`

### B12 · 窗口尺寸取决于坐标的物理像素对齐

**两条硬规则**（已升格为 `项目规则.md` **R-B08** + ADR-009）：

1. **构造参数 `width`/`height` 不可信** —— 请求 `360×44`，实测得到 `362×46` 甚至 `364×46`；
   创建后必须 `setBounds({width,height})` 校正一次（校正后完全幂等，连续 6 次写回 Δ=0）。
2. **坐标必须对齐物理像素网格** —— 步长 = 使 `step × scaleFactor` 为整数的最小正整数：
   `100%→1 · 125%→4 · 150%→2 · 175%→4`。不对齐的话，宽或高会自己多 `1px`。

实现在 `src/main/window.js` 的 `physicalGridStep()` / `alignToPhysicalGrid()`，
已接入**初始定位 / 边缘吸附 / 收起展开切换 / 跨屏移动**四条路径。

**复测**：`node tools/launch-electron.mjs experiments/exp-position-matrix.mjs`

### B13 · 主进程 `uncaughtException` 只打日志不退出

**现象**：`src/main/index.js` 末尾那段 `process.on('uncaughtException', …)` **只打日志、不退出**，
把 Node 默认的「崩溃即退出」改成了「带着未知状态继续跑」。

**原本的判断**：删掉这段就能恢复默认行为。

**实验结论：这个判断是错的。** 取证脚本 `experiments/diag-uncaught-exception.mjs`，
对照组（不注册任何监听器）vs 实验组（注册同款监听器）：

| 组 | 进组时 `listenerCount('uncaughtException')` | 抛异常后 |
|---|---|---|
| 对照组（脚本不注册） | **1** | **仍然存活**（3 次心跳后才被主动 `exit(99)`） |
| 实验组（注册同款） | 1 | 仍然存活（9 次心跳），handler 确实捕获到了 |

→ **Electron 自己就注册了 `uncaughtException` 监听器。** 所以光删掉 `index.js` 那段，
**不改变"半死"语义**；但那段仍有独立价值（带 `[main]` 前缀、可被本项目日志入口归因）。

**状态**：✅ **已闭环（2026-09-19）** —— 处置方案为「**落盘错误上下文 + 明确的退出策略**」，与 B3（日志与可观测性）合并处理。

实现在 **`src/main/crashlog.js`**（**零依赖**，有意不 import electron —— 注释里写明"请勿顺手优化掉"）：

| 失败种类 | 处置 | 为什么不这样不行 |
|---|---|---|
| `uncaughtException` | **同步落盘完整上下文 → `process.exit(1)`** | 同步异常之后进程状态未知。继续跑的代价是"行为异常却没有任何线索，且后续错误会级联污染日志" |
| `unhandledRejection` | **落盘，但不退出** | promise 拒绝通常是局部的、可恢复的。为此杀掉整个应用是把小病当绝症 |

**四个必须写下来、否则一定会被"优化"掉的决定**：

1. **必须同步写**（`writeFileSync`）—— 异步写在 `process.exit()` 之前根本来不及落盘。
2. **用 `process.exit` 而不是 `app.exit`** —— 崩溃路径上不该再依赖 Electron 的清理流程。
3. **崩溃标记读一次即消费**（`takePendingCrash()` 读完就删）—— 否则同一场崩溃会被反复报告。
4. **取走标记必须在任何可能抛异常的事情之前** —— 先取证，再干活，不然取证本身就丢了。

**离线考裁判**：`tools/test-crash-policy.mjs`（`npm run test:crash`）五关全部通过、退出码 0 ——
① uncaught → 退出码 1 + 落盘内容完整 ② 标记"报告一次即消费" ③ rejection → 退出码 0 且不生成崩溃标记
④ 纯函数边界 ⑤ **变异体必须落网**（"落盘但不退出"那个变异体给出退出码 0，反证断言确实有判别力）。

**运行时可见性**：心跳行里多了 `prev_crash=` 字段；自检日志新增「主进程失败记录」一段。
启动时若发现上次崩溃过，会打印 `[main] ⚠️ 上一次运行崩溃过：…`。

> **顺带逼出来的第二条规则**：这次拆分过程中发现，**判定逻辑只要还 import 着 electron，就永远测不了**。
> 于是有了 `项目规则.md` **R-B11**：「不需要 Electron 的逻辑，不许被 `electron` 的 import 绑架」。
> **而 R-B11 定下来的第一个动作，就当场抓出了自己的第一个违规** —— `blurmeasure.js`（登记为 TD-06）。
> **一条规则如果抓不到任何东西，说明它只是感想。**

> ⚠️ **这个实验本身踩了一个更隐蔽的坑，值得单独记住**：
> 第一版脚本**不建窗口**，两次运行都在"抛异常之前"就退出了（退出码 `0x80000003`），
> 看起来完全像"异常导致了退出"——**差点得出一个相反的结论**。
> 抓完整输出才发现真因是 GPU 进程反复崩溃（`GPU process isn't usable. Goodbye.`）：
> **本机"不建窗口的 Electron 主进程"根本活不下来**，与 `uncaughtException` 毫无关系。
> → 修法：脚本内建一个隐藏窗口，使运行环境与 `index.js` 一致。
> **教训：对照实验如果两组都死在同一个"与假设无关的原因"上，结论会完全反过来。**

**顺带发现（对 M1 有用）**：产品若有"无窗口阶段"（纯后台采集、仅托盘、开机预热），需要注意上面这个 GPU 崩溃特性。

**复测**：`node tools/launch-electron.mjs experiments/diag-uncaught-exception.mjs --handle`
