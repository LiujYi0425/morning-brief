## 数据不出本机（产品级承诺）

订阅列表是你的兴趣画像，API Key 是你的钱。**这两样都不会离开这台电脑。**

- 没有服务端（ADR-007 明确不做中转）
- API Key 用系统级加密存储，**渲染进程从设计上就拿不到它**（规则 R-E05）
- 抓取与模型调用全部发生在主进程，直连你自己的 Key

## M0 验出了什么（地基已经踩实的地方）

M0 不写产品功能，只回答一个问题：**这个平台靠不靠得住。** 结论是——**靠得住，但前提是你得知道它会怎么骗你。**

排查过程中抓出 **6 个静默失败级问题**（`B8–B13`，`docs/04-项目审查报告.md` §6 有全部取证），其中 **4 条已经变成代码层 / 规则层的强制约定**：

| 问题 | 一句话 | 现在的应对 |
|---|---|---|
| **B10** | ESM 主进程里顶层 `await app.whenReady()` 会**死锁**（Electron 要等入口模块求值完才发 ready） | 一律用 `.then()` → 规则 **R-B07** |
| **B11** | 环境里若有 `ELECTRON_RUN_AS_NODE=1`，`electron.exe` 会**静默退化成普通 Node**：不开窗口、不注入 API，报错还指向别处 | **只能经唯一入口启动**，由它在 spawn 前删掉该变量 → 规则 **R-B09** |
| **B12** | 窗口尺寸取决于**坐标的物理像素对齐**：请求 360×44，实得 364×46。构造参数 `width/height` **不可信** | `setBounds` 校正 + 坐标对齐物理像素网格 → 规则 **R-B08** / ADR-009 |
| **B13** | `uncaughtException` 之后进程"带伤继续跑"。**Electron 自己就注册了该监听器**，所以"删掉那段代码"**解决不了问题** | 由项目给出明确策略：同步落盘 + `process.exit(1)`；`unhandledRejection` 只落盘不退出 → 规则 **R-B10**（与 B3 日志体系合并处置） |

> **物理像素网格速记**：使 `步长 × 缩放比` 为整数的最小正整数。
> `100%→1 · 125%→4 · 150%→2 · 175%→4 · 200%→1`（150% 下坐标必须是偶数）。
>
> 另外两条踩过的坑（**B8 / B9**，未升级为规则，但已写进代码）：`file://` 下 CSP 的 `'self'` 可能匹配不上（要显式加 `file:` 源）；
> `sandbox: true` 时 preload **不能 require 本地文件**，得内联 + 开机自检。

**九条验收结果**：通过 **4** ｜ 不通过 0 ｜ 有保留 0 ｜ **无法验证 1（双屏，本机只有一块屏——这不是通过，是没条件测）** ｜ 待人工判定 **4**。

> **"自动可判的部分"已全部自动判完。** 剩下的 4 条 + 1 条无条件是**人眼 / 硬件条件**问题（对比度目视、全屏隐去、三档缩放需改系统设置、双屏需第二块屏），
> 不是代码问题 —— 详见 `项目计划工程书.md` §5.3 的 M0 任务表。**这才是"M0 收尾"的准确含义。**

## 日常操作

**每次改完文档或代码后**，跑一次同步校验：

```bash
node tools/sync-check.mjs
```

**全部通过** → 继续开发。**有 [FAIL]** → 先修同步，再继续。

> Windows 提示：终端若显示中文乱码，是控制台代码页的问题，不影响校验结果。
> 工具每次都会把同样的内容写一份 UTF-8 报告到 `tools/sync-report.txt`，随时可读。

**别信"我记得改过"。** M0 收尾时这套校验器第一次跑就报了 8 项 FAIL，**没有一项是文档内容写错**，
全是"改了正文漏了 frontmatter""改了 `depends_on` 漏了 `version`"这类半截编辑 —— 详见 `项目计划工程书.md` §7「1.2.0 同步校验结论」。

### 它检查八件事（2026-09-19 从 5 项扩到 8 项）

| # | 检查什么 | 不过会怎样 |
|---|---|---|
| 1 | 每份受管文件都有合法且完整的 frontmatter 元数据块 | FAIL |
| 2 | 声明的上游**确实存在**，且**版本匹配** | FAIL |
| 3 | 必需章节齐全（文档要「变更记录」；代理要七个章节） | FAIL |
| 4 | §6 同步矩阵**覆盖了所有 `doc_id`** | WARN |
| 5 | `agents/registry.json` 与 `agents/*.md` **实际内容一致** | WARN |
| 6 | **核对留痕** —— 第 2 项过了还不够，必须证明"你真的看过"（**新增**） | FAIL `[缺留痕]` |
| 7 | **表格完整性** —— 空行不许把一张表断成两截（**新增**） | WARN |
| 8 | **§6 同步矩阵里的版本号 vs frontmatter** —— 它现在是全库唯一的权威版本表（**新增**） | WARN |

> **第 2 项和第 6 项的区别，值得单独记一句** —— 这是整套机制最要紧的分工：
>
> - **第 2 项**只问"你声明的是最新版吗" → 那么**手改一个版本号就能骗过机器**。
> - **第 6 项**才问"**你到底看过没有**" → 它要求 `doc_id@版本` 这个字面量出现在你的变更记录里，
>   而一条合格的留痕长这样：`已核对 MASTER-PLAN@1.2.0，结论：其改动属记账类，本文件无需改动`。
>   **写下结论的过程，就是核对本身。**
>
> **⛔ 明确不算留痕的两处**：**frontmatter**（`depends_on: X@1.0.0` 那行**自身就含** `X@1.0.0`）和 **页脚**（`上游：X@1.0.0`）。
> 把它们算数等于**让检查自己满足自己** —— 这个洞在开发当天真的出现过，导致 **5 个文件靠页脚蒙混过关**。
> 详见 `项目计划工程书.md` §7「C+E 已上线」· 四。

> **第 7 项为什么值一条检查**：表格被空行断成两截时，Markdown 渲染出来只是"表格短了一截"，
> **看起来像是作者有意为之** —— 人眼审阅几乎必然放过。全库第一次跑就抓出 **7 处**，其中 2 处是编辑时刚埋下的。

> **第 8 项只报 WARN，是刻意的**："攒批"（把几件各自会触发级联的事攒起来一次做完）时，
> §6 会**故意**暂时落后 —— 那是有效的工作方式，不该被机器判成错误。但它**必须浮出来**，不能安静地留着。
> 这一项已做过**变异测试**：故意把 §6 里 `PROJECT-RULES` 的版本改成 1.3.0，它当场报出预期的 WARN。
> **抓不到已知缺陷的检查，等于没检查。**

**每完成一个阶段性任务后**，按 `项目计划工程书.md` §9 的收尾清单走一遍，更新三处：

## 四条最重要的约定

1. **变更先改计划书。** 顺序反了，代码和计划就会各说各话。
2. **需求先登记再执行。** 不在范围内的进 §3.3 待定区，不当场承诺。
3. **不确定就说不确定。** 必须区分「已验证」和「推测」。
4. **文档优先于代码。** 冲突时以文档为准，除非文档被证明是错的。

## 五条铁律

| | 铁律 |
|---|---|
| **L1** | 压缩优先 —— 宁可 5 条好的，不要 30 条平铺的 |
