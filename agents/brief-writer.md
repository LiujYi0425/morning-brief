# 代理 · brief-writer（简报生成）

## 职责

**一句话**：把一堆原始条目，压成一份人愿意读的简报。

**具体做的事**：

1. **去重**：URL 精确匹配 + 标题归一化相似度
2. **分组**：按主题粗聚类（规则优先，AI 兜底）
3. **筛序**：AI 打分排序，**只留前 8-12 条**（分层处理的第一层，便宜）
4. **摘要**：只对入选条目做深度摘要（分层处理的第二层，贵）
5. **成稿**：产出符合 `Brief` 契约的结构化数据

## 不负责

- ❌ **不采集**（那是 `collector` 的事）
- ❌ **不写界面**（那是渲染进程的事）
- ❌ **不做任何文件操作**（规则 R-E01）
- ❌ **不决定"要几条"** —— 上限由铁律 L1 和计划书 §1.2 定，不是它自己拍
- ❌ 不重试到成功为止 —— 模型调用失败要如实上报，不能假装成功
- ❌ **绝不接触 API Key** —— 客户端由上层注入且已持有 Key（ADR-007）。本代理**不读 Key、不传 Key、不把 Key 写进任何日志或产出物**（规则 R-E05）

> **最容易犯的错**：舍不得删。看到 30 条都觉得"这条也有用"。**记住铁律 L1：压缩率就是产品力。** 宁可给 5 条高质量的。

## 输入契约

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `items` | `NormalizedItem[]` | 是 | `collector` 的产出 |
| `date` | string | 是 | 简报日期，`YYYY-MM-DD` |
| `maxItems` | number | 否 | 简报条目上限，默认 12 |
| `historyHashes` | string[] | 否 | 近期已用过的 `hash`，用于跨天去重 |

**前置条件**：模型客户端已注入（**客户端由 `services/brief/generate.js` 持有，其 Key 来自 `services/security/keystore.js`**，见 ADR-007）；`items` 已通过 `collector` 的自检。

## 输出契约

```js
{
  brief: Brief,          // 见《工程架构文档》§4.2 的 Brief 结构
  stats: {
    input:      number,  // 输入条目数
    afterDedupe: number, // 去重后
    selected:   number,  // 最终入选
    compression: number, // 压缩率 = selected / input，目标 ≤ 5%
  },
  tokenUsed: number
}
```

**质量要求**：

- `summary`（总览句）必须是**一句人话**，不是关键词堆砌
- 每条 `digest` **≤ 2 行**，超出必须截断
- `groups` 按条目数降序；同数量按固定顺序（**布局稳定性，规则 R-C03**）
- `status` 必须如实反映：`ok` / `partial`（部分源失败）/ `failed` / `empty`

**失败时的行为**：

- 模型调用失败 → 重试 1 次；仍失败 → 返回 `status: 'failed'`，**不要编造内容**
- 部分源无数据 → `status: 'partial'`，并带上 `failedSources`

## 执行清单

> 每次运行按此清单执行，不要凭记忆。

1. **跨天去重**：用 `historyHashes` 先过滤掉近期已用过的条目
2. **批内去重**：URL 精确匹配 → 标题归一化相似度
3. **粗分组**：先按规则（来源 / 关键词）分，剩下的交 AI 兜底
4. **第一轮模型调用（筛选，便宜）**：批量送 15-20 条，只让它输出"重要性排序 + 分组归属"，**不要在这一步做摘要**
5. **截断**：按 `maxItems` 取前 N 条
6. **第二轮模型调用（摘要，贵）**：只对入选条目做深度摘要
7. **生成总览句**：基于入选内容写一句人话
8. **组装 `Brief`**：按契约结构输出，计算 `compression`
9. **上报用量**：`tokenUsed` 如实记录

> **第 4 步和第 6 步分离是本代理最重要的规则。** 合成一步会让成本失控（见《立项文档》§10）。

- [ ] 所有 `digest` 都不超过 2 行
