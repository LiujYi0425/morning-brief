# 晨报机 · 子代理机制

> 本文件定义项目里的"干活单元"：**怎么定义、怎么调用、怎么学习、怎么进化。**
>
> **一句话说清设计思路**：所谓"自动学习与迭代进化"，**不是指望模型自己变聪明，而是建立一条「经验 → 规则 → 执行清单」的闭环**。
> 代理每次任务后必须回答"这次学到了什么"，而教训必须**转化成可执行的规则**，否则就只是感想。

---

## 1. 为什么需要子代理

一个笼统的"帮我做这个功能"会遇到三个问题：

1. **职责不清** —— 没人知道边界在哪，越做越散
2. **经验不留存** —— 每次从零开始，同一个坑反复踩
3. **无法审查** —— 自己检查自己，等于没检查

子代理机制针对性地解决这三点：**明确契约**（解决 1）、**lessons 库**（解决 2）、**Critic 角色**（解决 3）。

---

## 2. 三类代理

| 类型 | 干什么 | 本项目实例 | 关键特征 |
|---|---|---|---|
| **Worker** | 干活，产出交付物 | `collector`、`brief-writer` | 有明确的输入输出契约 |
| **Critic** | 审查 Worker 的产出 | `design-critic`、`arch-critic` | **只提问题，不改东西**。与 Worker 分离是刻意的 |
| **Curator** | 维护其他代理 | `curator` | 读 lessons、决定升级/分裂/淘汰 |

**为什么 Critic 必须和 Worker 分开**：同一个角色既干活又检查自己，必然倾向于认为"我做得挺好"。分开之后，Critic 的唯一职责就是找问题。

## 3. 代理定义协议

每个代理是一个 Markdown 文件，位于 `agents/`，由 **元数据块 + 七个固定章节** 组成。

### 3.1 元数据块（必需，同步校验工具会读）

```
---
agent_id: <唯一标识，与文件名一致>
version: <语义化版本>
type: <worker | critic | curator>
updated: <YYYY-MM-DD>
status: <ACTIVE | DRAFT | DEPRECATED>
trigger: <什么情况下该调用它>
depends_on: <依赖的项目文档，如 ARCHITECTURE@1.0.0>
eval_score: <0-100，最近一次评估得分；null 表示尚未评估>
run_count: <累计运行次数>
success_count: <累计成功次数>
---
```

### 3.2 七个固定章节

| 章节 | 作用 |
|---|---|
| `## 职责` | 一句话说清它负责什么 |
| `## 不负责` | **明确边界**（和职责同等重要） |
| `## 输入契约` | 调用它必须提供什么 |
| `## 输出契约` | 它保证产出什么 |
| `## 执行清单` | 分步骤的操作规则（**这是 lessons 的沉淀地**） |
| `## 自检清单` | 它交付前必须自己过一遍的检查项 |
| `## Lessons` | 经验库，每次任务后追加 |

**`## 执行清单` 与 `## Lessons` 的关系是整个机制的心脏**：

```
Lessons 里的一条教训
   ↓  转化成可执行动作
执行清单里多一条规则
   ↓  下次运行自动生效
代理的行为改变了
```

**没有这个转化，Lessons 就只是一本日记。**

## 4. 调用协议

### 4.1 调用三件事

任何一次代理调用，都必须明确：

1. **哪个代理**（agent_id）
2. **输入**（按该代理的输入契约）
3. **期望输出**（按输出契约）

### 4.2 每次运行必须产出三样东西

| 产出 | 说明 |
|---|---|
| **交付物** | 按输出契约的实际结果 |
| **自评** | `confidence`（0-1）+ 不确定的地方**必须明说**（对应规则 R-A04） |
| **新教训** | 本次踩到的坑 / 发现的更优做法。**没有就写"无"，不允许留空** |

> 第三条是最容易被跳过、也最不能跳过的一条。**没有"新教训"的代理，是一个停止进化的代理。**

### 4.3 组合调用

Worker 之间按数据流串联：

```
collector  →  brief-writer  →  design-critic
（采集）      （生成简报）      （审查产出）
                    ↑
              arch-critic 可在任意环节介入
```

Critic 的意见由 Worker **显式处理**（规则 R-F05）：要么修，要么记录"已知晓，暂不修"+理由。**不允许静默忽略。**

## 5. 学习机制

### 5.1 Lessons 表的格式

每个代理文件末尾的 `## Lessons` 是一张表：

| 日期 | 场景 | 踩到的坑 / 发现 | 转化成的规则 | 应用版本 |
|---|---|---|---|---|
| 2026-09-18 | … | … | … | 1.0.1 |

**"转化成的规则"这一列不允许填"下次注意"。** 必须是一个具体的、下次能自动执行的动作，并且要真的写进 `## 执行清单`。

### 5.2 什么算"值得记的教训"

- ✅ 一个原本会失败的边界情况
- ✅ 一个更省时间/Token 的做法
- ✅ 一个契约描述不够清楚导致的返工
- ❌ "这次做得还行"（无信息量）
- ❌ 一次性的环境问题（不是可复用的知识）

### 5.3 学习不是自动发生的

必须有一个明确的动作触发：**每次代理任务结束后，立即更新它的 `run_count` / `success_count` / `Lessons`。**

这一步由 `curator` 负责催促和检查。**没有人催，学习就不会发生。**

## 6. 进化机制

### 6.1 三种进化动作

| 动作 | 触发条件 | 具体做法 |
|---|---|---|
| **晋升（Promote）** | Lessons 里积累了 2 条以上已转化的规则 | 把新规则合入 `## 执行清单`，升 minor 版本（1.0.0 → 1.1.0） |
| **分裂（Split）** | `## 执行清单` 超过 ~7 步，或职责横跨两个明显不同的领域 | 拆成两个代理，各自升到 1.0.0，原代理标记 DEPRECATED |
| **淘汰（Retire）** | 连续 3 次 `eval_score < 60` | 标记 DEPRECATED，由 curator 决定：重写 / 合并进别的代理 / 彻底删除 |

### 6.2 升级触发时机

- **每次任务后**：更新计数与 Lessons（轻量）
- **每 10 次运行** 或 **每次阶段收尾**：`curator` 做一次正式审查，决定是否晋升

**为什么设这两个时机**：前者保证经验不丢，后者保证不频繁折腾。**每次都升版本 = 版本号失去意义。**

### 6.3 版本号规则

| 变更 | 版本变化 |
|---|---|
| 补充 Lessons、修措辞 | patch（1.0.0 → 1.0.1） |
| 晋升新规则、改执行清单 | minor（1.0.1 → 1.1.0） |
| 改职责边界、改输入输出契约 | major（1.1.0 → 2.0.0） |

**改输入输出契约必须升 major**，因为下游调用方需要重新核对。

> ⚠️ **版本号有三个载体，必须同一次改完**：① frontmatter `version:` ② 文件末尾页脚 `*版本：…*` ③ `registry.json` 的 `version` 字段。
> **只改其中一个 = 留下一个不会被机器发现的假版本。** 2026-09-19 的核对中实际抓到过这个错误：四个代理定义的 frontmatter 已升版，**页脚却仍停在上一版**（`sync-check` 不读页脚，所以永远不会报错）。
> 这条属于「同一份受管文件必须整块一致修改」—— 该候选规则已登记在 `MASTER-PLAN` §7，**本次页脚漂移正是它的一个真实案例**。

### 6.4 升级必须留痕（规则 R-F03）

改代理定义 → 升版本 → 在 `registry.json` 和本文件 §7 各留一行。**不允许悄悄改行为。**

## 8. 与项目文档的同步

代理系统不是孤岛，它在三层结构里：

```
MASTER-PLAN          决定「做什么」—— 代理的目标来源
    ↓
PROJECT-RULES §F     决定「代理的规矩」—— 代理必须遵守 R-F01~R-F05
    ↓
AGENT-SYSTEM（本文件） 决定「代理怎么组织」
    ↓
agents/*.md          具体代理定义
```

**同步要求**：

| 触发 | 必须做的事 |
|---|---|
| 计划书升版本 | 检查 §3.1 的 `depends_on` 是否需要更新 |
| 项目规则 §F 有变动 | 逐个核对代理定义是否与规则冲突 |
| 代理升 major 版本 | 在 MASTER-PLAN §7 记一行（P2 级） |
