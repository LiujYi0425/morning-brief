# 晨报机 · 立项文档 v1.3.0

> 一款常驻桌面的个人信息简报工具。每天定时替你读完所有订阅源，把值得看的东西压成一张卡片，贴在桌面角落。
>
> 基座模型：deepseek-harness / DeepSeek-V4.1 Flash（创造模式）

---

## 一、一句话定义

**你的桌面情报板。** 你不用打开它、不用查收它，抬眼就能看到今天外面发生了什么。

---

## 二、目标用户与核心场景

**定位**：**服务自己和懂技术的朋友**（本版）。~~泛大众工具~~ → **已按 ADR-007 收窄**。

> **⚠️ 定位修订（2026-09-18，ADR-007）**：本文档初稿写的是"泛大众工具"。经用户决策，**本版明确不面向泛大众**——因为选择了"用户自带 API Key、不提供中转"，这天然把不懂技术的陌生人挡在门外。
>
> **这不是妥协，是取舍。** 换来的是：数据不出本机、无服务端运维责任、无持续成本、无合规负担。
>
> **泛大众化没有消失，进了待定区**（MASTER-PLAN §3.3）。重新评估的触发条件：① 有 ≥5 位非技术朋友主动表示想用；② 或 v1.0 稳定运行满 1 个月。**满足任一条再谈，不提前焦虑。**

**核心使用者画像**：投资人、行业观察者、产品/运营从业者、学生、技术人——**共同点是能自己搞到一个 API Key**。

**核心场景**（一句话能讲清的）：

> 早上到工位，端起水，眼角扫到桌角的卡片：「今天 12 条值得看，其中 3 条和你关注的 AI 芯片有关」。读五分钟，你就不用再刷任何资讯 App。

**它不是**：不是阅读器，不是 RSS 客户端，不是资讯 App。它不追求"你订阅的一切都给你"，恰好相反——**它追求"把 200 条压成 12 条"**。压缩率就是它的产品力。

## 三、产品形态：常驻桌面卡片

这是本项目最核心的形态决策，单独成节。

### 为什么是常驻卡片，而不是托盘弹窗

托盘弹窗的交互是"弹出 → 读完 → 消失"，属于**事件型**；常驻卡片属于**环境型**——它安静存在，你随时抬眼可看。

对"信息聚合与提醒"这件事，**环境型比事件型更合适**：因为信息的价值不在"被推送的那一刻"，而在"你刚好需要时它就在那儿"。而且常驻形态天然解决了冷启动问题——价值展示不需要用户做任何操作。

### 三种状态

| 状态 | 尺寸（基准） | 内容 | 进入方式 |
|---|---|---|---|
| **展开态** | 约 360 × 520 | 总览一句话 + 3-5 条重点 + 分组入口 | 点击收起条 / 快捷键 |
| **收起态** | 约 360 × 44 | 单行摘要："今天 12 条 · 3 条 AI 芯片" | 点击展开态标题栏 |
| **隐藏态** | — | 完全不可见 | 托盘图标 / 快捷键唤回 |

**默认启动状态：收起态。** 新用户第一眼看到一条安静的细带，不吓人、不占地方；想看得更多是他自己的选择。

### 交互细节（这些决定它"好不好相处"）

- **吸附边缘**：默认吸附屏幕右侧，可拖动到任意位置，记忆坐标
- **透明度**：**默认「安静」档（96%）**，提供安静 / 标准 / 通透三档预设，另在高级设置给无级滑块。
  > 早期草稿写的"默认 85% 不透明度"**已作废**——85% 在花哨壁纸上大概率不达 4.5:1 对比度（铁律 L3）。权威定义见《设计研究与页面架构规范》§3.3。
- **降级形态**：若 `backdrop-filter` 不可用或混合缩放渲染异常，自动切换为**不透明形态**（ADR-008）。降级形态是**一等公民**——仍保证完整可读性与全部 8 条动效，只是换成实底 + 描边 + 阴影
- **不抢焦点**：这一点极其关键。卡片必须做到"点它才响应"，绝不能你正在打字时它跳出来抢走输入焦点
- **不遮挡其他窗口**：卡片采用**置底层级**（ADR-012）—— **永远排在其他所有普通窗口下方**，用户一开窗口它就自动让位，**不需要任何"监听前台窗口"的逻辑**；看视频、演示时同样不会挡在前面。⚠️ **反向代价**：它也可能被别的窗口盖住而"一时找不到"，缓解方式见 §十二 R3
- **多显示器**：**按显示器分别记忆位置与状态**。
  > ⚠️ **已知技术难点（B1）**：透明无边框窗口 + 多显示器混合缩放（如 4K@150% + 1080p@100%）在 Electron 下存在 DPI 缺陷，`getPrimaryDisplay().scaleFactor` 在 v23+/Win11 22H2+ 常返回错误值 1.0。**M0 必须验证**（验收 6/7/8/9），应对方案见 ADR-008 降级模式与架构文档 `window_state` 表。
- **一键收起**：`Esc` 或快捷键立刻收起

### 技术实现路径

- **v0.1–v1.0 一律使用 Electron 无边框透明置底窗口**（**ADR-012**）：
  `frame: false` + `transparent: true` + `alwaysOnTop: false` + `skipTaskbar: true`，
  并由主进程把窗口压到**顶层 Z 序最底**（`SetWindowPos(HWND_BOTTOM)`）＋ `WS_EX_NOACTIVATE`（防抢焦点）。
  > **为什么不置顶**（ADR-005 原方案）：置顶意味着"能盖住其他应用窗口"，在产品上**不是收益，是干扰**（铁律 L2「不打扰优先」）。
  > **为什么不挂桌面层**（ADR-011 曾采用）：2026-09-22 **A10 实测判定桌面层窗口不会被合成到屏幕上** ⇒ 不可行。
  > 详见 `项目计划工程书.md` §4 M0 节末「A10 结论」与 `docs/03` **ADR-012**。
- **真正的桌面壁纸层组件（Windows 下挂到 WorkerW）不做**。它能实现"被其他窗口覆盖"的原生桌面小组件效果，但**实现方式依赖系统内部结构，系统更新容易打坏**（登记为 `项目计划工程书.md` §8 **R12**），**而且本机实测该方案在当前 Windows 版本下根本渲染不出来**。
  ⇒ **"被其他窗口覆盖"这个产品目标改由「置底顶层窗口」达成 —— 不需要动任何系统内部结构。**

## 四、信息源策略

本期只做两类源，都是低风险、高稳定性的。

### A 类：标准 RSS / 博客 / 新闻站

协议规范、几乎没有反爬、长期稳定性最好。这是**主力源**，v0.1 只做这一类。

### B 类：API 型源

数据最准、最结构化。候选清单及实现要点：

| 源 | 实现方式 | 备注 |
|---|---|---|
| GitHub Trending | **用 GitHub Search API 模拟**（`created:>7天前` + 按 stars 排序） | 比爬 Trending 页面稳得多 |
| 天气 | 和风天气 / OpenWeather | 需申请 Key，免费额度够个人用 |
| 日历 | 本地 ICS 文件 或 系统日历 | 纯本地，无外部依赖 |
| 股票 / 基金行情 | 第三方数据接口 | **授权与稳定性需单独验证，推迟到 v1.0 评估** |

> ⚠️ **每一类 API 源都要在接入前单独验证可用性与授权条款**，不要因为"看起来能用"就写进代码。行情类数据尤其要注意合规。

### 明确排除的源

**公众号 / 知乎 / 微博**：反爬最狠、稳定性最差、合规风险最高。虽然内容最想要，但本期一律不做。这类源会以极高的维护成本吃掉你所有的开发时间。

## 五、核心管线（7 步）

```
[1] 采集      定时器触发（默认每日 07:30，可配置）
      ↓
[2] 归一化    所有源统一为标准结构 {title, url, source, published, content}
      ↓
[3] 去重      URL 精确匹配 + 标题归一化相似度（v1.0 再评估向量方案）
      ↓
[4] 分组      按主题粗聚类（规则优先，AI 辅助兜底）
      ↓
[5] 筛序      AI 打重要性分，只留前 8-12 条进入深度摘要
      ↓
[6] 成稿      生成结构化简报 JSON（总览 + 分组 + 摘要 + 原文链接）
      ↓
[7] 呈现      渲染到桌面卡片 + 本地存档
```

**第 5 步的分层处理是整个管线的灵魂**：先让模型做一轮"快速筛选"（输入短、输出短、成本极低），再对入选条目做深度摘要。这样既省钱，又避免了"给每条都写摘要，结果用户只看前三条"的浪费。

## 八、技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 外壳 | **Electron** | 生态最成熟、资料最多、你最看得懂；无边框透明窗口开箱可用（**层级见 ADR-012：置底顶层窗口**） |
| 渲染 | 原生 HTML / CSS / JS（**不上框架**） | 第一版界面简单，框架只会增加阅读负担 |
| 存储 | SQLite（better-sqlite3） | 单文件、零配置、查询方便 |
| 抓取 | Node 原生 fetch + `rss-parser` | 依赖少，逻辑透明 |
| 调度 | `node-cron` | 一行配置搞定定时 |
| 模型 | DeepSeek-V4.1 Flash（官方 SDK 或直接 fetch） | 官方与 Flash 档位都很适合高频轻量调用 |
| **密钥存储** | **Electron `safeStorage`** | **用户自带 Key（ADR-007）→ 密钥安全成为本项目新增的一等关注点。密文落 `userData`，不进 SQLite、不进日志** |
| 打包 | electron-builder | 成熟、支持 Win/mac |

**关于 Tauri**：体积和内存确实更优，但需要 Rust 能力。既然你选了"想深度参与、看得懂"，第一版不要给自己加这层。等 v1.0 稳定后，如果体积/内存真成痛点，迁移是体力活而非智力活。

**关于"模型调用中转服务"（已决策不做）**：初稿曾把它列为 R6 的三个候选方案之一。**已否决（ADR-007）**——它会引入服务端运维责任、持续成本、以及"用户内容流经你服务器"的合规问题，与本项目"数据不出本机"的定位直接冲突。**用户自带 Key 是本版唯一方案。**

## 九、数据模型（简表）

| 表 | 关键字段 |
|---|---|
| `sources` | id, type(rss/api), name, url, enabled, last_fetch_at, health |
| `items` | id, source_id, title, url, published_at, content, hash, fetched_at |
| `briefs` | id, date, summary(总览一句话), groups(json), created_at, token_used |
| `brief_items` | brief_id, item_id, rank, section, ai_summary |
| `settings` | key, value（含 `renderMode`、`opacityLevel` 等） |
| `window_state` | display_id, dip_x, dip_y, w, h, state, updated_at |

**关键设计**：`items` 与 `briefs` 分离。条目是原始素材，简报是某一天的加工产物。同一条目可以被多天的简报复用（比如一条长期发酵的新闻），`hash` 字段负责跨天去重。

**`window_state` 按显示器分行**，而不是只存一组全局坐标——混合缩放环境下同一组 DIP 坐标在不同屏上的物理位置不同，只存一组会导致跨屏使用后"跳回主屏"或"掉到屏幕外"。**注意 `settings` 表不存 API Key**（见 §八 密钥存储与架构文档 §4.1 安全约束）。

## 十、Token 成本控制（必须从一开始就设计）

按 50 个源、每天约 300 条原始条目估算，**朴素做法（逐条送模型写摘要）成本会失控**。五条控制措施：

1. **批量而非逐条**：一次请求处理 15-20 条，而不是一条一请求
2. **本地预筛**：去重、正文截断（每条截取 1500 字符左右）、低价值源直接跳过
3. **缓存**：同一 URL 只总结一次，跨天复用
4. **分层处理**：先"快速筛选"（短输入短输出），再对入选的 8-12 条做深度摘要
5. **用量观测**：`briefs.token_used` 字段记录每日消耗，做到心里有数

> 以上数量级仅为设计参考，**实际消耗必须在 v0.1 阶段实测**，再调整源数量与摘要深度。

## 十二、风险与对策

| 编号 | 风险 | 对策 |
|---|---|---|
| **R1** | **冷启动**：新用户看到空列表就走 | 预置源包 + 首屏直接展示示例简报（**先展示，后配置**） |
| R2 | 抓取层不稳定，某个源挂了 | 每个源独立健康度；单源失败不阻塞整体；卡片上明示"3 个源今日抓取失败" |
| R3 | 常驻卡片遮挡 / 打扰 | 半透明 + 可收起 + 不抢焦点 + 全屏时自动隐去。**2026-09-22（ADR-012）**：置底层级**结构性解决了"卡片遮挡其他窗口"这一面**；**反向风险随之而来** —— 卡片会被任何普通窗口盖住 ⇒ 用户可能"忘了它还在"。缓解：收起态细带 ＋ 位置记忆 ＋ **不做自动弹出**（不用打扰换可见） |
| R4 | Token 成本失控 | 见第十节五条措施 + 每日用量统计 |
| R5 | API 源授权与合规 | 接入前逐个验证；行情类数据延后并单独评估 |
| ~~R6~~ | ~~**用户自配 API Key 的门槛**（泛大众的死结）~~ | ✅ **已闭环（2026-09-18，ADR-007）**。决策：**纯本地 · 用户自带 Key，不提供中转**。配套动作：① 首次启动向导含"一键申请引导"（讲清去哪申请、填哪一格）；② Key 用 `safeStorage` 加密存储；③ 泛大众化转入 MASTER-PLAN §3.3 待定区，附重新评估触发条件。**降级后的残余风险**：仍有非技术朋友可能卡在"申请 Key"这一步，故 M2 验收标准相应放宽为"五分钟 **+ 一次 API Key 配置**" |
| R7 | 简报质量平庸，"读起来像废话" | 压缩率是产品力。宁可只给 5 条高质量的，也不要给 30 条平铺的 |
| **R8** | **`backdrop-filter` 在 Electron 透明窗口中不可用** | M0 最先验证。**预案已升格为一等公民**（ADR-008）：不透明降级形态仍是完整产品，不是丑版兜底 |
| **R9** | **透明窗口 + 多显示器混合缩放的 DPI 缺陷**（`scaleFactor` 读取不可靠、跨屏坐标偏移） | 并入 M0 验收 6/7/8/9；架构侧按 `display_id` 分行记忆位置；若无法合理成本解决 → 触发 ADR-008 降级并把"混合缩放副屏"列为已知限制 |

**R1 是仍然可能杀死这个产品的头号风险**（R6 已闭环，转为"可接受的残余风险"）。R8/R9 都是 M0 必须一次性打掉的技术不确定性。

## 十三、明确不做的事

写下边界，比写下功能更重要：

- ❌ **不做导出分享**（已确认纯私人阅读，卡片本身就是终点）
- ❌ 不做公众号 / 知乎 / 微博抓取
- ❌ 不做手机推送
- ❌ 不做桌面壁纸层原生组件（**层级采用「置底顶层窗口」，见 ADR-012**）
- ❌ 不做账号体系 / 多用户
- ❌ **不做模型调用中转服务 / 不代付模型费用**（ADR-007。会引入服务端运维、持续成本与合规负担）
- ❌ 不做"你订阅的一切都给你"——**压缩才是这个产品的核心价值**
