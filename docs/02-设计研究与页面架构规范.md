> 前置文档：`docs/01-立项文档.md`（CHARTER）
> 本文件回答两个问题：**视觉与动效该怎么做**，以及**页面该怎么搭**。
> 本文件不含任何页面代码——它是写代码之前的依据。

# 第零部分 · 三条核心结论

如果只看一段，看这三条。后面所有内容都是它们的展开。

**结论一：可读性压倒一切，通透感是次要的。**
Apple 在 iOS 26 推出液态玻璃，因透明度过高被大量吐槽"背景一复杂就看不清字"；iOS 27（本周 9 月 14–15 日刚推送）最大的改动就是**修正可读性**——提高对比度、新增全局透明度滑块、深色模式自动降透明。而我们的卡片要贴在**任意一张壁纸**上（可能是花哨的风景照），风险比 Apple 更高。**所以本项目的默认策略是"实底色 + 极薄透光"，不是"全透 + 模糊"。**

**结论二：严格区分「内容层」与「功能层」，玻璃只属于功能层。**
这是 Apple HIG 目前最明确的一条规则：Liquid Glass 是**漂浮在内容之上的功能层**，绝不能用于内容层。滥用它会让层级混乱、可读性崩塌。本项目把这条当作铁律。

**结论三：动效只做三件事，其余一律不做。**
Apple 明确说"不要为了动而动"，且"频繁发生的交互通常不该加动效"。一个每天被看一次的常驻卡片，动效预算极少：**展开/收起、卡片出现、刷新反馈**。就这三件。

# 第一部分 · 调研综述

## 1.1 iOS 27 与液态玻璃：一次"可读性纠错"的完整教训

时间线值得记住：

| 时间 | 事件 |
|---|---|
| 2025-06-09 | WWDC 发布 Liquid Glass，宣称"玻璃的光学特性 + 流体感" |
| 2025-09 | iOS 26 正式推送，大规模吐槽透明度过高、文字可读性差 |
| 2026-09-14/15 | iOS 27 推送，**核心改动是修可读性** |

iOS 27 具体做了什么（对我们的设计有直接指导意义）：

1. **提高对比度**，解决 iOS 26 "背景一复杂就看不清字"的问题
2. **新增 Liquid Glass 无级调节滑块**——从"极致通透"到"完全不透明"，全局生效
3. **深色模式下系统自动降低透明度**（自动降透明来保可读性）
4. **强制第三方键盘与第三方 App 原生菜单适配**，提升视觉统一性
5. 图标重绘，"更清晰锐利、层次感更强"

**我们能学到的**：连 Apple 这种级别的团队，把"通透"做到极致之后都不得不往回撤。这说明**透明度的默认值应该偏保守，并且必须给用户一个能自己调的出口。**

顺带一提，iOS 27 还新增了"超大尺寸小组件"（可占满主屏）——小组件这个形态正在被系统级重视，这是个好信号。

## 1.2 两个层：内容层与功能层

> Apple HIG 原文要点：Liquid Glass 构成一个**独立的功能层**，让控件与导航浮在内容层之上，从而在功能元素与内容之间建立清晰的视觉层级。
>
> **"不要在内容层使用 Liquid Glass。"**

| 层 | 装什么 | 用什么材质 |
|---|---|---|
| **功能层**（在上） | 导航、标题栏、工具条、按钮、浮动操作、分组标签 | Liquid Glass / 玻璃材质 |
| **内容层**（在下） | 文章、数据、列表、卡片内容本身 | 标准材质（实底、低透明） |

**Apple 的另一条重要提醒**：内容层里可以有例外——像滑块、开关这类**瞬时交互元素**，在用户激活它的那一刻可以临时获得玻璃外观，用来强调"我现在可以操作"。这个细节很妙，值得记下来。

**还有一个警告**：不要在滚动视图里放玻璃层。玻璃是"固定层"的材质；如果它跟着内容滚动，会和导航层撞在一起。Apple 原话大意是——内容层是滚动的那一层，导航层才是用玻璃的那一层。

## 1.3 材质分级

### 玻璃的两个变体

| 变体 | 行为 | 何时用 |
|---|---|---|
| **regular（常规）** | 模糊并调整背景亮度以保证文字可读 | **默认**。背景可能造成可读性问题时、组件有大量文字时（弹窗、侧边栏、气泡） |
| **clear（清澈）** | 高度透明，优先展示底下的内容 | 只在**视觉丰富的背景**（照片、视频）之上使用，且需谨慎 |

**clear 的关键配套规则**：如果底层内容偏亮，需要在其后加一层 **35% 不透明度的暗色压底**，否则对比度不够。

### 标准材质的四档（内容层用）

| 档位 | 透明度 | 适用 |
|---|---|---|
| `ultraThin` | 最透 | 全屏视图、需要浅色方案时 |
| `thin` | 较透 | 部分遮挡内容的浮层 |
| `regular` | 中（默认） | 常规浮层 |
| `thick` | 最实 | 需要深色方案、或需要与下层明确区分 |

**选择原则**：厚材质（更不透明）→ 对小字号、细笔画元素提供更好的对比度；薄材质（更透明）→ 让用户保持对背景的感知，知道自己身处何处。

## 1.4 色彩：vibrancy（振动色）的概念

在有材质的表面上，**不要用普通颜色，要用"振动色"**——系统定义的、专门为材质表面调过的色板。原因是材质会随环境明暗变化，普通颜色会在某些背景下过暗、过亮、过饱和或对比不足。

层级用 vibrancy 等级表达：

| 等级 | 用途 |
|---|---|
| `label` | 标准正文（对比最高） |
| `secondaryLabel` | 描述性文字、副标题、脚注 |
| `tertiaryLabel` | 非活动元素，仅在不需要高可读性时使用 |
| `quaternaryLabel` | 对比最低，**一般不要在 thin / ultraThin 材质上用**（对比不足） |

**对我们的启示**：卡片上不要用"绝对色值"，要用**语义色 + 随背景自动调整**的思路。至少要实现"同一套语义色在浅色背景和深色背景下都能达标"。

## 1.5 2026 年视觉趋势清单（及采纳判断）

| 趋势 | 是什么 | 本项目判断 |
|---|---|---|
| **Bento Grid 2.0** | 大小不一的模块化卡片，用面积表达信息权重 | ⚠️ **取思想，不取形式**。卡片空间太小，硬套网格会碎。但"用面积表达权重"这条直接采纳 |
| **Glassmorphism 2.0** | 玻璃拟态成熟版，克制、服务层级而非炫技 | ✅ **有限采纳**，仅用于功能层 |
| **AI-Adaptive Interface** | 界面按用户角色/行为/时间动态重排 | ❌ **明确拒绝**（见 2.2） |
| **Dark-First Design** | 暗色作为设计起点而非事后套壳 | ✅ 采纳"双模对等"，但**不设 dark 为唯一默认** |
| **3D & Spatial UI** | WebGL/Three.js 的空间化界面 | ❌ 拒绝。常驻卡片必须零 GPU 负担 |
| **Kinetic Typography** | 动态字体、滚动响应式排版 | ❌ 拒绝。常驻元素持续运动 = 干扰源 |
| **Micro-interaction System** | 微交互系统化，统一反馈语言 | ✅ 采纳（但极简，见第四部分） |
| **Scroll Storytelling** | 滚动叙事 | ❌ 卡片内容不做长滚动 |
| **Voice & Multimodal UI** | 语音与多模态输入 | ⏸ 推迟。v1.0 后再评估 |
| **Sustainable Performance** | 把速度、体积、能耗纳入设计决策 | ✅ 采纳，且对本项目权重很高 |

**趋势清单的正确用法**：不是"用了什么效果"，而是"这个趋势解决什么问题"。上面打了 ❌ 的六个，全都因为同一个理由——**它们服务于"吸引注意"，而我们的产品服务于"不打扰"。**

## 1.6 动效：曲线、时长与弹簧

### 核心曲线（社区共识值）

| 曲线名 | 值 | 用途 |
|---|---|---|
| **Enter**（进场） | `cubic-bezier(0.22, 1, 0.36, 1)` | 元素进入、基于 transform 的 hover |
| **Move**（位移） | `cubic-bezier(0.25, 1, 0.5, 1)` | 滑动、抽屉、面板 |
| **Drawer / iOS-like** | `cubic-bezier(0.32, 0.72, 0, 1)` | iOS 风格的抽屉/面板 |
| **Material 3 emphasized** | `cubic-bezier(0.2, 0, 0, 1)` | 主导性界面变化（前 20% 时间走完 80% 距离） |
| **Overshoot（弹簧）** | `cubic-bezier(0.34, 1.56, 0.64, 1)` | 成功反馈，慎用 |

### 时长基准

| 场景 | 时长 | 曲线 |
|---|---|---|
| 按下反馈 | 100–160ms | Enter |
| Tooltip / 小气泡 | 125–200ms | Enter 或 ease-out |
| 下拉/选择器 | 150–250ms | Enter |
| 弹窗 / 抽屉 | 200–350ms | Enter |
| 屏幕内位移 | 200–300ms | Move |
| 简单 hover（色/透明） | 200ms | ease |

**通用区间**：绝大多数 UI 动效应在 **150–350ms**。低于 100ms 感觉像瞬移（失去了过渡的意义），高于 400ms 用户会觉得"我在等界面"。装饰性/环境性动效可以更长。

### 三条反直觉但重要的规则

1. **进场用 decelerate，退场用 accelerate**（ease-out 进、ease-in 出）。反了会显得诡异——ease-in 进场的弹窗会给人"犹豫一下然后突然弹出来"的感觉。
2. **退场要比进场快。** 用户的心理预期是"我让它消失，它就该立刻消失"。对称的进出时长是常见错误。
3. **不要用 `scale(0)` 起点。** 现实里没有东西是从"无"里出现的。用 `scale(0.85–0.95)`。

### 弹簧：什么时候用，什么时候别用

- ✅ **适合**：加入收藏（心形 0 → 1.2 → 1）、抽屉把手的回弹、对勾笔画的完成
- ❌ **不适合**：任何 hover（频率太高，显得杂乱）、**退出动画**（用户期待"消失"，回弹在空间逻辑上不对）、**弹窗进场**（稳定减速更有质感）
- **经验值**：一屏一两个弹簧元素就够了

### 其他硬规则

- **拖拽期间元素要锁死在指针上，松手之后才加缓动。**
- **过渡必须是可打断的**（retarget 而不是重启）。快速反复切换时不能从头播。
- **每个弹簧都必须有降级路径**（`prefers-reduced-motion`）。
- **不要在挂载时播动画**——用户没有触发的动效会让人迷失方向。
- **不要用 keyframes 做高频触发的元素**，用 transition（keyframes 无法优雅打断）。

## 1.7 性能与无障碍：不可协商的底线

### 性能

- **只动 `transform` 和 `opacity`**——这两个属性跳过 layout 和 paint，由 GPU 合成
- **不要动** `width` / `height` / `top` / `left` / `margin` / `padding`（触发全页重排）
- **不要动** `box-shadow` / `border-radius`（触发重绘）
- `will-change` **只在动画期间加，结束后移除**，不要常驻
- 用 `IntersectionObserver` 暂停离屏的循环动画
- **不要用 `transition: all`**——会触发意外的属性动画

### 无障碍

```css
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: 0.01ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 0.01ms !important;
  }
}
```

这条是**不可协商的**。有前庭功能敏感的用户会因为弹性动效产生真实的眩晕感。

同时注意：**动效不能是传达重要信息的唯一方式**（Apple：用触觉、声音等其他方式补充）。

# 第二部分 · 从调研到本项目的取舍

## 2.1 桌面常驻卡片的特殊性

**我们不是做 iOS App，也不是做官网。** 两者的经验都不能直接照搬。差异清单：

| 维度 | iOS App / 官网 | 晨报机（桌面常驻卡片） |
|---|---|---|
| 背景 | 系统提供，可控 | **用户的桌面壁纸，完全不可控** |
| 观看时长 | 主动使用，几分钟到几十分钟 | **被动扫视，几秒** |
| 出现频率 | 用户主动打开 | **常驻可见，一天扫几十次** |
| 空间 | 全屏 | **约 360×520 的一小块，和一堆窗口抢地盘** |
| 用户耐心 | 较高 | **极低——它是我桌面上"多出来的东西"，随时可以被关掉** |
| 系统能力 | 可以用系统的无障碍设施 | **得自己保证一切** |

**最要命的一条是最后那个"多出来的东西"**。用户对常驻工具的容忍度天然低于对主动打开的工具。它不能吵、不能亮、不能动、不能占地方，否则就被关掉。

## 2.2 明确拒绝"AI 自适应界面"

2026 年的趋势里有一条是"界面根据用户行为动态调整布局"。**对官网是亮点，对常驻工具是灾难。**

理由很简单：**常驻工具的可用性建立在位置稳定性上。** 用户是靠肌肉记忆找东西的——"总览在最上面，分组标题在下面，刷新按钮在右下角"。如果每天布局都在变，用户每次都要重新找一遍，这带来的挫败感远远大于"个性化推荐"带来的收益。

**我们的立场：布局绝对稳定。可变化只发生在内容层（今天有几条、是哪几条），而不发生在结构层（哪块在哪）。**

## 2.3 采用清单

| 决策 | 来源 | 在本项目的落地 |
|---|---|---|
| 内容层 / 功能层分离 | Apple HIG | **铁律**。玻璃只用于标题栏、底栏、按钮 |
| `regular` 玻璃变体为默认 | Apple HIG | 默认使用 regular，不用 clear |
| 不用 clear glass | Apple HIG | 卡片下方是壁纸，属于"视觉丰富背景"，但我们选择**不做效果，直接实底** |
| 透明度保守 + 可调 | iOS 27 教训 | 默认偏实，提供 3 档预设，高级设置给无级滑块 |
| 深色模式自动降透明 | iOS 27 | 采纳（暗色下背景对比更复杂） |
| 用面积表达信息权重 | Bento Grid 2.0 | 采纳（总览行占用最宽的行，条目紧凑排列） |
| 双模对等设计 | Dark-First Design | 采纳，浅/深两套都要测对比度 |
| Enter / Move 曲线 | 动效社区共识 | 直接采用 |
| 退场快于进场 | 动效社区共识 | 直接采用 |
| 无弹簧回弹 | Apple HIG + 社区 | 本项目无"成功时刻"，不需要 |
| 只动 transform / opacity | 性能共识 | 唯一例外见 4.4（展开/收起） |
| `prefers-reduced-motion` | 无障碍底线 | 强制实现 |
| 拒绝 3D / 动态字体 / 滚动叙事 / 自适应布局 | 判断 | 见 2.2 与 1.5 |
| **双形态对等**（玻璃 / 不透明） | ADR-008 | **一等公民**。形态差异只活在 `surface.css`，组件不知情（§3.7） |
| **不做"透明度 = 1"式降级** | ADR-008 推导 | 降级形态靠描边 + 阴影重建边界，且描边/阴影都比玻璃态更重 |
| **不透明形态下隐藏透明度选择器** | ADR-008 推导 | 没有档位可选的东西不要放在界面上 |

## 2.4 关于"阴影"的例外说明

Apple HIG 的立场是"除功能性焦点环外不要阴影"。**但那是针对全屏 App——背景由系统控制，控件靠材质就能浮起来。**

我们的情况不同：卡片贴在用户壁纸上，**必须从壁纸中"浮"起来**，否则视觉上会糊成一团。所以这里需要一个例外：

```
浅色模式：box-shadow: 0 8px 32px rgba(0,0,0,0.12), 0 1px 2px rgba(0,0,0,0.06)
深色模式：box-shadow: 0 8px 32px rgba(0,0,0,0.45)
加 0.5px 内描边（对应 Apple 说的 "outer highlights"）做边缘定义
```

**这是有理由的例外，不是随手加的装饰。**

# 第三部分 · 设计令牌系统

## 3.1 色彩令牌（语义化，双模对等）

**原则**：令牌描述**用途**，不描述**外观**。叫 `text-primary`，不叫 `gray-900`。

### 中性阶层

| 令牌 | 浅色 | 深色 | 用途 |
|---|---|---|---|
| `surface-card` | `#FFFFFF` @ 94% | `#1C1C1E` @ 94% | 卡片主底 |
| `surface-raised` | `#F7F7F8` | `#2C2C2E` | 卡片内次级面（分组块、骨架） |
| `surface-overlay` | `#FFFFFF` @ 72% + blur(24px) | `#2C2C2E` @ 72% + blur(24px) | **功能层**（标题栏、底栏） |
| `border-hairline` | `rgba(0,0,0,0.08)` | `rgba(255,255,255,0.10)` | 0.5px 描边 |
| `border-divider` | `rgba(0,0,0,0.06)` | `rgba(255,255,255,0.08)` | 分隔线 |

### 文本阶层（对应 vibrancy 等级）

| 令牌 | 浅色 | 深色 | 用途 |
|---|---|---|---|
| `text-primary` | `#1C1C1E` | `rgba(255,255,255,0.92)` | 总览句、条目标题 |
| `text-secondary` | `rgba(60,60,67,0.60)` | `rgba(235,235,245,0.60)` | 条目摘要 |
| `text-tertiary` | `rgba(60,60,67,0.30)` | `rgba(235,235,245,0.30)` | 元信息、计数、时间 |

### 语义色（仅用于状态，不用于装饰）

| 令牌 | 浅色 | 深色 | 用途 |
|---|---|---|---|
| `accent` | `#0F6E56` | `#5DCAA5` | 分组色条、状态点、可交互焦点 |
| `state-ok` | `#1D9E75` | `#5DCAA5` | 抓取正常 |
| `state-warn` | `#BA7517` | `#EF9F27` | 部分源失败 |
| `state-error` | `#A32D2D` | `#F09595` | 全部失败 / 无内容 |
| `state-idle` | `rgba(60,60,67,0.30)` | `rgba(235,235,245,0.30)` | 未配置 / 未更新 |

**强调色的使用纪律**：整个界面里，强调色只出现在**三个地方**——分组左侧色条、状态圆点、焦点环。不超过这三处。这是"环境型工具不该抢注意力"的直接落地。

## 3.2 材质令牌

| 令牌 | 定义 | 用在哪 |
|---|---|---|
| `material-base` | 实底 @ 94% 不透明 + `backdrop-filter: blur(20px)` | 卡片本体 |
| `material-functional` | 半透 @ 72% + `backdrop-filter: blur(24px) saturate(1.4)` | 标题栏、底栏 |
| `material-transient` | 同 functional，但仅在激活瞬间生效 | 滑块的拖动把手等 |

**注意**：整张卡片只用**两层材质**（base + functional）。**绝不做玻璃叠玻璃**——Apple 明确指出玻璃层互相叠加会"collision"，导致层级崩塌。

## 3.3 透明度预设（回应 iOS 27 的教训）

| 档位 | backdrop alpha | 说明 |
|---|---|---|
| **安静** ✅ **默认值** | 96% | 几乎实底，任何壁纸上都清晰。**新装用户的初始值** |
| **标准** | 94% | 用户主动调低一档时的选择 |
| **通透** | 86% | 能感到壁纸，但仍保证对比度达标。**需要用户显式选择** |
| ~~无级~~ | — | 放进"高级设置"，附一句提示："调得太透会影响文字清晰度" |

> **⚠️ 默认值唯一性（G1 修正）**：本表**只能有一个默认值**——即「安静 96%」。
> 修正前本表出现"安静=推荐默认"与"标准=默认值"两处自相矛盾的表述，属于文档缺陷，已于 2026-09-18 修正。
> **裁定依据**：铁律 L3（可读性优先）+ iOS 27 的教训（连 Apple 都不得不把透明度往回收）。
> 一个贴在任何壁纸上的卡片，**没有理由在初始状态下就赌用户壁纸不花哨**。

**深色模式自动降一档**（比如用户选了"通透"，系统是深色时按"标准"渲染）。
**降级形态（ADR-008）下本表失效**——不透明模式没有透明度档位，`TransparencyPicker` 组件整体隐藏（见 §3.7）。

**硬约束**：**无论哪一档，正文文本与背后内容的对比度必须 ≥ 4.5:1。** 这是上线前的强制检查项。

## 3.7 双形态令牌（ADR-008 · 不透明降级为一等公民）

> **这一节是 ADR-008 在设计侧的落点。** 它约束的不是"好不好看"，而是"**万一玻璃做不出来，产品还能不能见人**"。

### 为什么需要它

M0 要验证两件事，两件都可能失败：

| 风险 | 可能性 | 失败后果 |
|---|---|---|
| R8：`backdrop-filter` 在 Electron 透明窗口中静默失效 | 中 | 玻璃形态整个不存在 |
| B1：多显示器混合缩放的 DPI 缺陷 | 中 | 双屏用户看到模糊 / 拉伸 |

**如果到那时才发现，代价是重写所有组件样式。**
**如果现在就分好层，代价只是多写一屏变量。**

### 分层原则：形态差异只活在令牌层

```
tokens.css        ← 基础量：字阶、间距、动效曲线、语义色。跨形态不变
surface.css       ← 形态量：背景、描边、阴影、虚化强度。随形态整体替换
    ↓
组件 CSS / JS     ← 完全不知道自己在哪个形态里
```

**铁律：组件里禁止出现「硬编码的形态值」——写死的 `blur` 数值、半透明 `rgba()` 的具体值、阴影的具体值。**
**允许（且要求）写 `backdrop-filter: var(--card-blur)` 这类「引用令牌」的形式：禁令针对的是「值」，不是「属性名」。**
**形态切换 = 在 `<html>` 上切一个 `data-surface` 属性。** 一次属性赋值，零组件改动。

> ⚠️ **措辞更正（2026-09-19）**：上面这一行原来写的是「组件里禁止出现 `backdrop-filter`」，
> 与同一句话后半段的「一律走令牌变量」**自相矛盾** —— `backdrop-filter` 要"走令牌"，
> 就**必然**要在组件里写出这个属性。原措辞把「属性名」和「值」混为一谈，
> 后果不是"读起来别扭"，而是**照字面执行会得出错误结论**：
> `m0-probe/src/renderer/styles/card.css` 里那 5 处 `backdrop-filter: var(--…-blur)`
> 会被判成违规 —— 而它们恰恰是这条规则**要求**的标准写法。
> 现已改为「禁止硬编码的**值**」。同步修正处：S-01、`surface.css` 头部、`card.css` 头部。

### 两套形态量对照

| 令牌 | `[data-surface="glass"]` | `[data-surface="opaque"]` |
|---|---|---|
| `--card-bg` | 实底 @94% 不透明（见 §3.3） | **纯实色**。浅色 `#FFFFFF`／深色 `#1C1C1E` |
| `--card-blur` | `blur(20px)` | `none` |
| `--card-border` | `0.5px` 内描边，`rgba(0,0,0,0.08)` | **`1px` 实描边**，`rgba(0,0,0,0.12)`（更明显） |
| `--card-shadow` | `0 8px 32px rgba(0,0,0,0.12)` | **`0 12px 40px rgba(0,0,0,0.20)`**（更重） |
| `--functional-bg` | 半透 @72% + `blur(24px) saturate(1.4)` | 纯实色 `#F2F2F7`／`#2C2C2E` |
| `--functional-border-bottom` | 无（靠材质分层） | **`0.5px` 分隔线**（必须补，否则功能层与内容层糊在一起） |

### 关键：降级不是"把透明度改成 1"

**这是最容易做糙的地方。** 直接设 `opacity: 1` 会得到一张"贴在壁纸上的白纸"——**没有边界感，比玻璃形态更难看**。

降级形态要靠**描边 + 阴影**重新建立"浮起来"的感觉：描边负责边界，阴影负责高度。两者都要比玻璃形态**更重**。

### 强制规则

| 编号 | 规则 |
|---|---|
| **S-01** | 组件 CSS 禁止出现**硬编码的形态值** —— 写死的 `blur` 数值、半透明 `rgba()` 的具体值、阴影的具体值。**「引用令牌」的写法（如 `backdrop-filter: var(--card-blur)`）是要求，不是禁止** —— 禁令针对的是「值」，不是「属性名」（见 §3.7 的措辞更正说明） |
| **S-02** | 新增任何"形态量"令牌时，**必须同时填两列**。填不全 = 文档缺陷 |
| **S-03** | 降级形态必须**独立通过**对比度检查（≥ 4.5:1）。**不能只测玻璃形态** |
| **S-04** | 初始形态由主进程探测决定，用户可手动覆盖，**手动选择优先且持久化** |
| **S-05** | 降级形态下的 8 条动效（第六部分）**一条都不减**。降级的是材质，不是交互品质 |

> **S-05 值得单独强调**：降级模式如果连动效都砍掉，就变成了"残废版"。
> 用户选择/遭遇降级，不该被罚一次体验降级。

# 第四部分 · 页面架构

## 4.1 信息层级

只有三级，外加一层"层级外元素"。**层级超过三层，扫视就会变成阅读——而我们的用户只会扫视。**

```
L1  总览句          ← 唯一允许"大声"的元素。14px/500
      ↓
L2  分组标题 + 计数   ← 结构锚点。13px/500 + 12px/计数
      ↓
L3  条目            ← 可扫视的碎片。13px/400，最多 2 行截断
─────────────────────────
L0  元信息 / 按钮    ← 时间戳、状态点、刷新、设置。12px/tertiary
```

**优先级规则（打架时按此裁决）**：

1. 总览句永远优先于一切——它必须出现在无需滚动的位置
2. 分组按**条目数降序**，同数量按**人工固定顺序**（不要按"重要性"随机排序，会破坏位置稳定性）
3. 单条摘要**最多 2 行**。超出用省略号，点击展开全文（在新窗口或跳原文）
4. **总条数上限 12 条**。这是硬约束——**压缩率就是产品力**。宁可只给 5 条好的，也不要给 30 条平铺的

**空状态的信息设计**（容易被忽视但很重要）：

- 未配置源 → 「还没有订阅源」+ 一个"载入推荐源包"的按钮
- 今天没有新条目 → 「今天没有新的动静」+ 上次更新时间的相对时间（"3 小时前看过"）
- 全部抓取失败 → 「今天有 5 个源没能连上」+ 错误原因 + 重试按钮

**三条空状态都必须有明确的下一个动作**，绝不能只显示一句"暂无数据"。

## 4.2 布局结构

### 收起态（默认启动状态）

```
┌──────────────────────────────────────┐  高 44px
│ ● 晨报 · 今天 12 条 · 3 条 AI 芯片  ⌄ │  宽 360px
└──────────────────────────────────────┘
 ↑状态点  ↑标题  ↑一句话摘要（自动截断）  ↑展开
```

信息分配：状态点 8px｜标题｜摘要（flex: 1，溢出省略）｜展开箭头
**这个高度是固定值 44px，不随内容变化。** 位置稳定性优先。

### 展开态

```
┌────────────────────────────────────────┐  ─┐
│ 晨报 · 9月18日 周五      12 条   收起  │   │ 功能层：material-functional
├────────────────────────────────────────┤  ─┤  ← 玻璃与内容的分界线
│                                        │   │
│  今天最值得看的是 AI 芯片与国产替代      │   │  L1 总览区（固定，不滚动）
│                                        │   │
│  ▍AI 与算力                      3 条  │   │  L2
│    · 某厂商发布新一代推理芯片……         │   │  L3
│    · 开源模型在中文评测上首次超越……     │   │  L3
│                                        │   │
│  ▍行业动态                        2 条  │   │  L2
│    · 国产替代订单同比增长 35%……        │   │  L3
│                                        │   │
│  ┈┈┈┈ 内容区可滚动 ┈┈┈┈                │   │  内容层：material-base
│                                        │   │
├────────────────────────────────────────┤  ─┤
│                        刷新     设置     │   │ 功能层：material-functional
└────────────────────────────────────────┘  ─┘
   宽 360px ｜ 展开态高 520px（内容多则滚动，高度不变）
```

**关键布局决策：总览区固定在顶部，不参与滚动。** 用户打开卡片的第一眼必须看到总览句，而不是"上次滚动到哪儿了"。只有分组列表滚动。

**底栏永远在屏幕内**——它是功能层，不属于滚动内容。这和 Apple 说的"内容层滚动，导航层固定"是同一个道理。

## 4.4 模块衔接逻辑

这一节回答"各个块之间怎么接上"，是最容易做糙的地方。

### 衔接点一：收起 ⇄ 展开

**核心原则：不是"换一个界面"，而是"同一个元素长大"。**

- ❌ 错误做法：隐藏 `CollapsedBar`，显示 `ExpandedCard`。视觉上是硬切，用户会丢失空间感
- ✅ 正确做法：**同一个容器**做形变，高度从 44px → 520px

**性能例外说明**：这里要动 `height`，违反了 1.7 的"只动 transform/opacity"规则。理由是**这是低频操作**（一天几次），不是每帧动画。配套要求：

1. 动画期间加 `will-change: height`，结束后立刻移除
2. 内部内容用 `opacity` + `translateY(4px)` 做次级动效，**延迟 40ms** 启动（错开，避免堆在一起）
3. 收起方向的时长（220ms）**短于**展开（280ms）
4. **必须可打断**——展开到一半再点收起，不能从头播
5. 实测若掉帧，改用 View Transitions API

### 衔接点二：刷新

**不用旋转菊花。** 理由是：旋转菊花传达的是"不知道还要多久"，而骨架屏传达的是"内容正在这里出现"。后者更有掌控感。

- 刷新时：`CardBody` 淡出（120ms）→ 骨架屏淡入 → 数据回来后骨架屏交叉淡出 → 内容淡入
- 顶栏的 `RefreshButton` 变成一个**极细的进度条**（2px，走 `--ease-move`），而不是转圈
- 必须支持"刷新中也能读旧内容"——**不要把用户正在看的内容抹掉**

### 衔接点三：新一天的简报到来

**这是本项目最容易被做坏、也最值得精心设计的一处。**

情境：早上 7:30 新简报生成好了，但用户此刻可能正在读昨天的内容（或者刚从睡眠中唤醒电脑）。

- ❌ 错误做法：直接替换内容。用户会瞬间迷失，且感到"我的东西被人动了"
- ✅ 正确做法：**不强行替换。** 在收起条的 `StatusDot` 上显示一个"新内容"标记（微弱的强调色呼吸，只呼吸 3 次就停，不做永久循环）。用户点击时才切换，切换时用 300ms 的交叉淡出淡入

这条设计同时满足了 Apple 的两条原则：**"让人们可以取消动效"** 和 **"不要打断"**。

### 衔接点四：状态流转

```
                    ┌──────────────┐
   首次启动 ──────→ │  未配置       │
                    └──────┬───────┘
                           │ 载入推荐源包
                           ▼
                    ┌──────────────┐
                    │  加载中       │ ←── 定时触发 / 手动刷新
                    └──────┬───────┘
                           │
              ┌────────────┼────────────┐
              ▼            ▼            ▼
        ┌─────────┐  ┌─────────┐  ┌─────────┐
        │ 有内容   │  │ 今日无新 │  │ 抓取失败 │
        └────┬────┘  └────┬────┘  └────┬────┘
             │            │            │
             └────────────┴────────────┘
                          │ 次日 07:30 / 手动刷新
                          └──→ 回到「加载中」
```

**每个状态都必须有出路。** 任何"卡在某个状态出不来"的路径都是 bug。

### 衔接点五：数据流

```
主进程
  定时器触发
    ↓
  采集（RSS / API）
    ↓
  归一化 → 去重 → 分组
    ↓
  模型调用（筛选 → 深度摘要）
    ↓
  简报 JSON 落库
    ↓
  ─── IPC ───→ 渲染进程
                 ↓
              卡片渲染
```

**渲染进程不做任何 AI 调用、不做任何抓取。** 它只负责画。所有重活都在主进程。这样卡片的响应永远是即时的——**一个每秒可能被扫视的常驻窗口，不能有任何主线程阻塞。**

# 第六部分 · 动效清单

**全项目只有 8 条动效。** 新增任何一条都要先回答："它是不是替代了某个信息？"答不上来就不加。

| # | 动效 | 触发 | 时长 | 曲线 | 动什么 | reduced-motion 降级 |
|---|---|---|---|---|---|---|
| 1 | 展开 | 点击收起条 | 280ms | Move | height + 内部 opacity/translateY(延迟 40ms) | 直接切换 |
| 2 | 收起 | 点击收起按钮 / Esc | 220ms | Move | 同上 | 直接切换 |
| 3 | 卡片首次出现 | 每天首次启动 | 300ms | Enter | opacity 0→1 + translateY(8px→0) | 直接显示 |
| 4 | 刷新过渡 | 手动 / 定时刷新 | 120ms 出 + 180ms 入 | Enter | opacity 交叉 | 直接替换 |
| 5 | 刷新进度条 | 刷新期间 | 持续 | Move | scaleX | 改为静态文字"更新中" |
| 6 | 新内容提示 | 有新简报到达 | 呼吸 3 次 × 1.2s | ease-in-out | opacity 0.6↔1 | 改为静态实心点 |
| 7 | 条目 hover | 指针移入 | 120ms | Enter | background-color | 直接变色 |
| 8 | 按钮按下 | 按下 | 100ms | Enter | scale(0.96) | 直接变色 |

**明确不做的动效**（写下来避免以后手痒）：

- ❌ 卡片入场不做回弹——每天看一次的常驻元素，回弹会很烦
- ❌ 不做视差滚动
- ❌ 不做文字逐字出现
- ❌ 不做图标常驻旋转（@keyframes 循环也避免）
- ❌ 不做 hover 时的弹簧
- ❌ 不做任何超过 400ms 的动效
- ❌ 不做 `transition: all`

## 附 · 一句话总结

**这个产品的设计目标不是"让人惊艳"，而是"让人安心地不用管它"。**

所有的克制——不做回弹、不做自适应重排、不做 3D、把透明度调保守、把条数压到 12 条——都服务于同一件事：**让它在桌角安安静静地待着，你抬眼看到它的时候，刚好知道该知道的事。**
