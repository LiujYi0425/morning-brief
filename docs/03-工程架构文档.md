# 晨报机 · 工程架构文档

> 本文件回答：**代码怎么搭、模块怎么分、以后怎么扩展。**
> 它与《设计研究与页面架构规范》分工明确：
> ——设计规范说"长什么样、怎么动"，本文件说"代码怎么组织"。

---

## 1. 架构总览

### 1.1 三层结构

```
┌──────────────────────────────────────────────────┐
│  渲染进程 (Renderer)                              │
│  只负责画。不做抓取、不做 AI、不做解析。            │
│  HTML + CSS + 原生 JS（不上框架）                  │
└───────────────┬──────────────────────────────────┘
                │  contextBridge（安全桥）
┌───────────────┴──────────────────────────────────┐
│  预加载 (Preload)                                 │
│  唯一的通信边界。白名单式暴露 API，不做逻辑。       │
└───────────────┬──────────────────────────────────┘
                │  IPC（命名通道）
┌───────────────┴──────────────────────────────────┐
│  主进程 (Main)                                     │
│  所有重活：采集 → 处理 → 模型 → 存储 → 调度        │
└──────────────────────────────────────────────────┘
```

**为什么这样切**：铁律 L4（渲染进程不做重活）。卡片每秒可能被扫视，主线程一旦阻塞，用户立刻能感觉到。所有耗时操作都被推到主进程，渲染进程拿到的永远是已经算好的数据。

### 1.2 数据流（唯一一条主链路）

```
scheduler（定时触发 / 手动触发）
    ↓
collect    采集：RSS / API → 原始条目
    ↓
normalize  归一化：统一成 NormalizedItem
    ↓
dedupe     去重：URL 精确 + 标题相似度
    ↓
group      分组：按主题粗聚类
    ↓
rank       筛选：AI 打分，只留前 8-12 条      ← 分层处理的第一层（便宜）
    ↓
brief      摘要：对入选条目做深度摘要          ← 分层处理的第二层（贵）
    ↓
store      落库：briefs / brief_items
    ↓
IPC 推送 → renderer 渲染
```

**分层处理是成本控制的核心**（见《立项文档》§10）：先用短输入短输出筛一轮，再对少数条目花钱做深度摘要。千万不要给每条都写摘要。

```
│   ├── scheduler.js          定时调度
│   └── services/

│                             ⚠️ sandbox: true 下无法 require 本地文件，

│
├── renderer/                 渲染进程
│   ├── index.html
│   ├── styles/

│   │   ├── surface.css       ★ 双形态令牌：glass / opaque（ADR-008）
│   │   ├── atoms.css
│   │   ├── molecules.css
│   │   └── organisms.css

│   │   ├── atoms/
│   │   ├── molecules/
│   │   └── organisms/
│   └── app.js                状态编排 + 渲染

└── shared/
    ├── contract.js           数据契约常量（IPC 通道名、枚举）
    └── schema.js             数据结构定义与校验

tools/                        ← ★ M0 新增（ADR-010）
├── launch-electron.mjs       ★ 唯一 Electron 启动入口：净化环境 + 守护开机心跳
└── win-display-facts.ps1     ★ Windows 独立裁判：直接问系统要物理分辨率/坐标/logPixels
```

**`tools/` 为什么必须进产品工程**：`launch-electron.mjs` 不是开发便利工具，是**正确性前提**——
少了它，`ELECTRON_RUN_AS_NODE` 一旦存在，应用会静默不启动（R-B09 / ADR-010）。
`win-display-facts.ps1` 是 `scaleFactor` 的**外部基准**，少了它，DPI 相关结论就退化为"只凭 Electron 自己说"。

**`surface.css` 独立于 `tokens.css` 的理由**：`tokens.css` 是"设计系统的基础量"（色彩、字阶、间距、动效曲线），**跨形态不变**；`surface.css` 是"形态相关的量"（背景、描边、阴影、虚化强度），**随形态整体替换**。把两者混在一起，切换形态时就会误伤基础量。这是 ADR-008 对目录结构的唯一要求——**一条清晰的分界线**。

## 3. 模块划分与依赖方向

### 3.1 依赖方向铁律

**依赖只能单向流动。反向依赖一律视为架构违规。**

```
renderer  ──IPC──▶  main/services
                      │
                      ▼
              collect → process → brief
                      │
                      ▼
                    store
```

| 规则 | 说明 |
|---|---|
| **D1** | `renderer` 不得直接依赖 `main`。只能通过 IPC 通道通信 |
| **D2** | `store` 是底层，**不依赖任何上层模块** |
| **D3** | `collect` 不认识 `brief`。采集层只产出 `NormalizedItem[]`，不关心后续怎么用 |
| **D4** | `process` 是纯函数层。给定输入必得相同输出，**不做 IO、不调模型**（`rank` 例外，它调 AI，但只依赖注入的 client） |
| **D5** | `brief` 是唯一允许调用模型的层（`rank` 的 AI 调用通过它注入） |
| **D6** | `shared/contract.js` 是全项目唯一的"词汇表"。**不允许在别处硬编码 IPC 通道名或枚举值** |

### 3.2 为什么这些规则重要

**D3 是最关键的一条。** 采集层如果"知道"了下游要干什么，就会开始做下游的活（比如自己写摘要）。半年后你会得到一堆互相纠缠的代码，改一处崩三处。

**D4 让处理层可以被单独测试。** 纯函数意味着喂固定输入就能验证输出，不需要启动整个应用。

**D6 让重构变便宜。** 通道名改一次，全局生效，而不是 grep 二十个文件。

## 4. 数据契约

### 4.1 IPC 通道（命名规范：`域:动作`）

| 通道 | 方向 | 载荷 | 用途 |
|---|---|---|---|
| `brief:get` | R → M | `{ date? }` | 取指定日期的简报（默认今天） |
| `brief:refresh` | R → M | — | 手动触发一次采集 |
| `brief:updated` | M → R | `Brief` | 主进程推送给渲染进程（新简报就绪） |
| `brief:progress` | M → R | `{ stage, percent }` | 刷新进度（用于 2px 进度条） |
| `window:setState` | R → M | `'collapsed' \| 'expanded' \| 'hidden'` | 切换卡片三态 |
| `window:getBounds` | R → M | — | 取当前位置与所在屏幕 |
| `settings:get` | R → M | `{ key }` | 读设置 |
| `settings:set` | R → M | `{ key, value }` | 写设置 |
| `sources:list` | R → M | — | 列出所有源及健康度 |
| `sources:update` | R → M | `{ id, patch }` | 增删改源 |
| `capability:report` | M → R | `{ backdropFilter: bool, scaleFactor, displays[] }` | 启动探测结果，决定初始渲染形态（ADR-008） |
| `apikey:status` | R → M | — | 查询 Key 是否已配置、是否可用。**永不返回 Key 明文** |
| `apikey:set` | R → M | `{ key }` | 写入 Key（主进程内用 `safeStorage` 加密后落盘） |
| `apikey:clear` | R → M | — | 清除已存 Key |
| `apikey:test` | R → M | — | 发起一次最小化连通性测试，返回 `{ ok, model, message }` |

**规则**：新增通道必须同时更新 `shared/contract.js` 和本表。

**安全约束（ADR-007 衍生，必须遵守）**：

1. **API Key 绝不以明文进入 SQLite、日志、崩溃报告、IPC 载荷回传。** 存储走 Electron `safeStorage.encryptString()`，密文落 `userData` 下的独立文件，**不进 `settings` 表**（表会被导出/备份，容易外泄）。
2. `apikey:status` 只返回布尔与元信息（如 `{ configured: true, maskedTail: '••••1234' }`），**没有"读回明文"这个通道**。渲染进程从设计上就拿不到 Key。
3. 所有网络请求在主进程发起，Key 只作为请求头在内存中短暂存在。渲染进程发不出任何携带 Key 的请求（D1 的直接收益）。
4. 若 `safeStorage.isEncryptionAvailable()` 为 false（部分 Linux/无钥匙串环境），**必须明示用户并让用户选择"仅本次会话内存持有"或"明文落盘（不推荐）"**，不允许静默降级为明文。

### 4.2 核心数据结构

**NormalizedItem**（采集层的统一产物）

```js
{
  id:        string,   // 稳定哈希
  sourceId:  string,
  title:     string,
  url:       string,
  published: number,   // 时间戳
  content:   string,   // 正文，截断至 ~1500 字符
  lang:      string,
  hash:      string    // 跨天去重用的标题+来源指纹
}
```

**Brief**（渲染进程唯一需要认识的结构）

```js
{
  id:        string,
  date:      string,   // YYYY-MM-DD
  summary:   string,   // 总览一句话（L1）
  groups: [
    {
      name:  string,   // 分组名（L2）
      count: number,
      items: [
        {
          title:  string,   // L3
          digest: string,   // 摘要，≤2 行
          url:    string,
          source: string
        }
      ]
    }
  ],
  status:    'ok' | 'partial' | 'failed' | 'empty',
  failedSources: string[],
  tokenUsed: number,
  createdAt: number
}
```

**关键设计**：`Brief` 已经是对外契约，**渲染进程不需要知道任何采集/处理细节**。这是 D1 的具体体现。

### 4.3 数据库结构

| 表 | 关键字段 | 说明 |
|---|---|---|
| `sources` | id, type, name, url, enabled, last_fetch_at, health | 源配置 + 健康度 |
| `items` | id, source_id, title, url, published_at, content, hash, fetched_at | 原始条目 |
| `briefs` | id, date, summary, groups(json), status, token_used, created_at | 简报 |
| `brief_items` | brief_id, item_id, rank, section, ai_summary | 简报与条目的关联 |
| `settings` | key, value | 键值设置（含 `renderMode`、`opacityLevel` 等） |
| `window_state` | display_id, dip_x, dip_y, w, h, state, updated_at | **按显示器分别记忆位置**（B1 验收 8 的前提） |

**设计要点**：`items` 与 `briefs` 分离。条目是原始素材，简报是某一天的加工产物。同一条目可被多天简报复用（长期发酵的新闻），靠 `hash` 跨天去重。

**`window_state` 按 `display_id` 分行，而不是只存一组全局坐标。** 原因：混合缩放环境下，同一组 DIP 坐标在主屏（150%）和副屏（100%）对应的物理位置完全不同。若只存一组坐标，用户把卡片拖到副屏后关机，下次启动它会"跳回主屏"或"掉到屏幕外"。**按屏记忆是唯一正确的做法。**

**注意**：`settings` 表**不存 API Key**。原因见 §4.1 安全约束第 1 条。

## 5. 扩展点

> **这一节决定了架构"灵活不灵活"。** 判断标准是：加一个新东西，需要动几个文件？

### 5.1 加一个信息源

**需要动的文件：1 个（新增），1 个（注册）**

1. 在 `services/collect/adapters/` 新建适配器，实现统一接口：

```js
export default {
  id: 'adapter-id',
  type: 'rss' | 'api',
  async fetch(source) → NormalizedItem[]
}
```

2. 在 `adapters/registry.js` 注册

**不需要动**：处理层、简报层、存储层、渲染层。**一个新源不应该让任何现有模块改一行代码。** 如果需要改，说明接口设计有问题——改接口，不要改模块。

### 5.2 加一个界面组件

**需要动的文件：3 个**

1. 按设计规范 §4.3 确认它属于哪一层（原子/分子/组织）
2. 新建组件文件
3. 在 `styles/` 对应层级的 CSS 里加样式

**强制要求**：必须同时定义完整状态矩阵（R-C06）。

### 5.3 加一条动效

**必须先过 R-C04 审查**（"它是不是替代了某个信息？"）。

通过后：
1. 用 `tokens.css` 里已有的时长/曲线变量，**不允许硬编码**
2. 必须写 `prefers-reduced-motion` 降级（R-C05）
3. 更新设计规范 §第六部分动效清单

### 5.4 加一个新的展示位（比如"今日待办"）

这类需求最容易引发架构腐化。**正确姿势**：

1. 先判断它是**新的数据源**还是**新的展示形式**
2. 新数据源 → 走 5.1 路径（采集层加适配器）
3. 新展示形式 → 走 5.2 路径（渲染层加组件）
4. **如果它需要新的数据流**（比如要写回、要交互）→ **走 P1 变更流程**，不允许临时接线

### 5.5 加一个渲染形态（玻璃 ↔ 不透明降级）⭐

> 这是 ADR-008 在架构上的落点。**双形态不是补丁，是从第一天就要留好的口子。**

**核心原则：形态差异只允许存在于「令牌层」，不允许渗进组件层。**

```
tokens.css
  ├── [data-surface="glass"]    ← 玻璃形态：半透明 + backdrop-filter
  └── [data-surface="opaque"]   ← 降级形态：实色底 + 阴影描边
        ↓ 只换变量值，不换类名
     atoms.css / molecules.css / organisms.css
        ↓ 组件代码完全不知道自己在哪个形态里
     components/**
```

**实现约定**：

1. 组件里**禁止出现** `backdrop-filter`、`rgba(...)` 半透明值、硬编码阴影。这些一律通过令牌变量表达。
2. 形态切换 = 在 `<html>` 上切 `data-surface` 属性。**一次 DOM 属性赋值，不改任何组件。**
3. 降级形态必须**独立定义一整套令牌**（背景/描边/阴影/文字对比度），而不是"把透明度改成 1"。原因：纯实色底在浅色壁纸下反而不如玻璃有层次，需要靠**描边 + 阴影**重新建立边界。
4. 初始形态由主进程探测决定（见 §4.1 `capability:report`），用户可在设置里手动覆盖（`settings.renderMode: 'auto' | 'glass' | 'opaque'`），**手动选择必须持久化且优先于自动探测**。

**为什么值得这么设计**：如果不预留这个口子，等 M0 验证发现玻璃不可行时，代价是"重写所有组件的样式"。预留之后，代价是"多写一屏变量定义"。这是典型的**用 20 行的前瞻，换 2000 行的返工**。

### 5.6 加/改窗口几何（尺寸与坐标）⭐ M0 新增

> 这是 ADR-009 在架构上的落点。**窗口几何有一组平台硬规则，不遵守就会悄悄错 1~4px。**

**两条必须遵守的规则**（原始数据见 `m0-probe/report/winsize3-matrix.txt`）：

**规则一：构造参数里的 `width` / `height` 不可信。**

```js
// ❌ 错误：以为这样就得到 360×44
const win = new BrowserWindow({ width: 360, height: 44, /* ... */ });

// ✅ 正确：构造之后必须校正一次
const win = new BrowserWindow({ width: 360, height: 44, /* ... */ });
win.setBounds({ x, y, width: 360, height: 44 });   // ← 精确命中，且完全幂等
```

实测：请求 `360×44`，构造出来是 `362×46`；把窗口挪个位置甚至能到 `364×46`。
而 `setBounds` 校正之后，连续 6 次"原样写回"偏差全为 `0`。**注意这个偏差与"透明/无边框"无关** —— 带真边框的 `frame:true` 也一样偏。

**规则二：坐标必须对齐到物理像素网格。**

```js
// src/main/window.js
export function physicalGridStep(scale) {  // 使 step×scale 为整数的最小 step
  for (let n = 1; n <= 32; n += 1) {
    if (Math.abs(n * scale - Math.round(n * scale)) < 1e-6) return n;
  }
  return 1;
}
export function alignToPhysicalGrid(x, y, scale) { /* ... */ }
```

各缩放档位的步长：**`100%→1 · 125%→4 · 150%→2 · 175%→4 · 200%→1`**

**为什么**：实测规律 100% 一致 —— 坐标若落在非整数物理像素上（150% 下即奇数），窗口宽或高会自己多 `1px`：

| x | x×1.5 | 读回尺寸 | 结论 |
|---|---|---|---|
| 700 | 1050（整数） | `360×44` | ✅ 精确 |
| 701 | 1051.5（非整数） | `361×44` | ✗ 宽 +1 |
| 702 | 1053（整数） | `360×44` | ✅ 精确 |
| 703 | 1054.5（非整数） | `361×44` | ✗ 宽 +1 |

且**与是否靠近屏幕边缘完全无关**（远离边缘 / 靠近边缘 / 紧贴边缘三组实验表现相同）。
`y` 方向同理：`y` 为奇数时**高度** +1。

**必须接入的四个位置**（漏一个就会出现"有时精确有时不精确"的玄学 bug）：

1. 初始定位（`initialPosition`）
2. 边缘吸附（`snapToEdge`）
3. 收起/展开切换（`setCardState`）
4. 跨屏移动（`window:moveToDisplay`）

**机制未定论，这没关系**：疑似 Electron 在 DIP↔物理换算时对边界分别取整，但项目**不依赖对机制的解释** ——
规律稳定到可以据此制定规则，就照规则做，并把不确定性记在这里（见 TD-04）。

### 5.7 加一条新的平台能力（必须同时加一次探针）⭐ M0 新增

> 这是 R11「平台静默失败」在流程上的落点。

M0 一口气抓到 **6 个问题**（B8–B13）—— 其中 5 个是"不报错、不崩溃，只是结果不对"的静默失败，
第 6 个（B13）把「崩溃即退出」悄悄换成了「带伤继续跑」。
这说明这类问题**成片出现**，不是孤例。因此立一条流程约定：

**每当要新用一层 Electron / Chromium 的平台能力（窗口几何、显示器、GPU、快捷键、系统集成、电源事件……），
必须先写一个"独立裁判"或"对照实验"，拿到可信读数，再写业务代码。**

具体要求：

1. **给平台找独立裁判**。平台自己的读数不能自证。
   例：`scaleFactor` 的可信度靠"PowerShell 直接问 Windows 要物理分辨率"来交叉校验（见 §4.1 `capability:report`）。
2. **能对照的就对照**。别只测一种配置 —— 至少要有 `baseline` 与一种"反例"（如 `transparent:false`、`frame:true`）。
3. **实验脚本与原始输出一起留档**，否则结论不可复现、不可推翻。
4. **静默失败要变成可判定信号**。例：主进程启动即写"开机心跳"，启动器盯着它；没等到就报警并列出可能原因。

**为什么值得**：M0 的 6 个坑，没有一个能在规划阶段推演出来。**真跑一遍是唯一的方法。**

### 5.8 拆零依赖模块，让逻辑能在无头环境被验证 ⭐ 2026-09-19 新增

> 这是 **R-B11** 在架构上的落点，也是"考裁判"能在 CI / 沙箱里真正跑起来的前提。

**约定**：凡是不需要 Electron 就能完成的逻辑（判定、策略、映射、校验），**必须拆成零依赖模块**，
再由需要 Electron 的文件去 import 它。

```
src/main/
├── focus-verdict.js   ← 零依赖：三个计数器 → 三态结论（pass / fail / invalid）
├── crashlog.js        ← 零依赖：失败语义（同步落盘 + 明确退出策略）
├── window.js          ← import electron  →  同时 import focus-verdict.js
└── index.js           ← import electron  →  同时 import crashlog.js
```

> ⚠️ **注意 `blurmeasure.js` 不在这张名单里** —— 它 `import * as win from './window.js'`，
> 因此**不是**零依赖。这恰好是最遗憾的一处：它是全项目**最需要**离线验证的模块
> （像素判定 + 阈值 + 内建校准），却因为一行 import 被绑在了 GUI 运行时上，
> 目前只能靠 `npm run selftest` 真跑一次。**已登记为 TD-06** ——
> 这是本规则自己抓出来的**第一个违规**，而且是被它"核对而不是假设"抓到的。

**为什么这不是"为了好看而分层"**：`import { app } from 'electron'` 的代价**不是多一个依赖**，
而是**让整块逻辑只能在"能启动一个 GUI 进程的环境"里被验证**。
一旦环境不允许（CI、沙箱、远程会话），这块逻辑就**永远测不了** ——
而它看起来只是"环境限制"，一点都不像缺陷。**这是最容易被接受的一种技术债。**

**收益（已实测，不是设想）**：
- `tools/test-focus-verdict.mjs` —— 纯 Node，9 条用例 + 3 个变异体，秒级完成；
- `tools/test-crash-policy.mjs` —— 纯 Node，**真的触发一次崩溃**，断言退出码、落盘内容、标记消费语义。

两者都在 `npm test` 里。**需要 Electron 的那两项（`calibrate` / `selftest`）另算** ——
不许拿离线结果冒充它们：离线验的是**判定**，真跑验的是**采集**。

**判定问句**：这段代码里**出现过 `electron` 这个名字吗**？没有 → 它就不该待在 import 了 electron 的文件里。

## 7. 技术债登记

> **主动把债写下来，是唯一避免它变成"说不清的痛"的方法。**
> 每一项必须有：偿还触发条件。没有触发条件的债 = 永远不会还。

| 编号 | 债务描述 | 产生原因 | 影响 | 偿还触发条件 | 状态 |
|---|---|---|---|---|---|
| **TD-01** | 双形态令牌需成对维护，新增令牌时容易只改 `glass` 忘了 `opaque` | ADR-008 选择"完整覆盖"而非"只做玻璃" | 某形态下组件视觉崩坏，且**因为平时只看一个形态，很难被发现** | 出现**第一次"漏改"**时立即处理：加 lint 规则或双形态快照测试 | 🟡 待观察 |
| **TD-02** | `safeStorage` 在无系统钥匙串的环境不可用 | Electron 跨平台差异 | 该环境无法持久化 Key，每次启动需重填；或需用户接受不推荐的明文方案 | 有真实用户反馈"每次都要重填"时，评估引入第三方钥匙串库 | 🟡 待观察 |
| **TD-03** | `window_state` 按 `display_id` 记忆，但显示器 ID 在换线/换口/改分辨率时可能变化 | 操作系统不保证 display id 长期稳定 | 记忆失效，卡片回到默认位置（**可接受，不致命**） | 若用户体感上反复遇到，改为"分辨率 + 相对位置指纹"匹配 | 🟡 待观察 |
| **TD-04** | 物理像素网格步长的推导依赖"缩放比是有限小数"这一前提；遇到极罕见缩放比（如 1.333…）时 `physicalGridStep` 会在 32 次内找不到整数解而**退化为 1**（即放弃对齐） | ADR-009 用"找最小整数解"代替了对 DIP↔物理换算机制的解释 | 该缩放比下坐标无法对齐，窗口尺寸可能仍偏 1px。**不会崩，只是回到"未对齐"状态** | 出现该缩放比的真实用户反馈时：改为"按物理像素直接算目标 DIP 坐标"，或引入 `screen.dipToScreenPoint` 反推。**复测脚本已就绪**：`experiments/exp-position-matrix.mjs` | 🟡 待观察，风险很低 |
| **TD-05** | `setBounds` 校正 + 网格对齐这套动作目前散落在四个调用点，靠"记得都要接"维持 | ADR-009 落地时选择了显式调用而非统一封装 | 将来新增窗口移动路径时可能漏接，表现为"有时精确有时不精确" | **出现第一次"漏接"时立刻封装**成 `setCardBounds(x, y, w, h)` 单一入口，让调用方无法漏 | 🟡 待观察（M0 探针已用注释在四个位置互相指认） |
| **TD-06** | `blurmeasure.js` 通过 `import * as win from './window.js'` 被绑在 Electron 上，导致它**最核心的阈值判定与内建校准无法离线验证** | M0 实现时为了复用「展开卡片 → 截图」这套动作，直接 import 了 `window.js`，**没有把纯像素数学与 Electron 编排分开**。纯的部分（`extractGray`、`laplacianVariance`、几何推导、阈值比较）本来一行 electron 都不需要 | 拉普拉斯方差、区域带定义、阈值比较、校准判据**全都要真跑一次 Electron 才能验**；在 CI / 沙箱里这一块约等于**没有测试**。而它恰恰是"最容易悄悄给错结论"的那一块（一个拍脑袋的阈值会安安静静地年年报绿） | **下次动 `blurmeasure.js` 时立刻拆**（不要为了拆而拆）：把纯像素数学移入零依赖模块（如 `lapvar.js`），配一个纯 Node 的**变异测试**（阈值边界、纯色背景假阴性、校准态判据）。**判定问句已经有了**：那些函数里出现过 `electron` 吗？ | 🔴 **已识别，待偿还**（2026-09-19 由 R-B11 的核对动作发现） |

## 附 · 架构自检清单

**每次改动代码后，问自己七个问题：**

- [ ] **依赖有没有反向？**（D1–D6）
- [ ] **新增的通道名/枚举值有没有写进 `shared/contract.js`？**（D6）— 若同时改了 preload 的内联副本，**两处都改了吗？**（B8）
- [ ] **加新东西动了几个文件？** 超过 3 个就要问：是不是接口设计有问题？
- [ ] **有没有新产生的技术债没登记？**
- [ ] **我碰的样式是"基础量"还是"形态量"？** 形态量必须**两个形态各写一份**（ADR-008）
- [ ] **动过窗口几何吗？** 尺寸有没有 `setBounds` 校正？坐标有没有走 `alignToPhysicalGrid`？（ADR-009，四个调用点都接了吗）
- [ ] **主进程里有没有出现顶层 `await app.whenReady()`？**（R-B07 — 有就是死锁，一个窗口都不会出现）
